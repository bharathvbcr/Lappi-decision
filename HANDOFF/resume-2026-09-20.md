# RESUME lane — 2026-09-20

**A rental interrupted at minute 110 was not recoverable, and the reason was not that
checkpointing was missing.** The `Checkpoint` type existed, `train_cpt`/`train_ft` carried
`on_checkpoint` and `resume_from`, and `python/tests/test_trainer.py` proved a kill at
half-way reproduces the loss trajectory bit-exactly. Every piece was there. Three separate
things meant none of it reached a disk you could come back to:

* **No caller passed the hooks.** `on_checkpoint` is referenced in `trainer.py`,
  `byte_train.py` and the tests, and nowhere else. `Checkpoint.write` and `Checkpoint.read`
  are called in exactly two files, both of them test files. No driver in `tools/` writes a
  checkpoint, so nothing on disk survives a kill.
* **The one torch-backed step in the package produced a checkpoint that could not be
  written at all.** Measured on torch 2.12.1: `Rung0Step.state()` returned live tensors,
  `Checkpoint(...)` accepted them, `to_json()` accepted them, and `write()` raised
  `TypeError: Object of type Tensor is not JSON serializable`. A run finds that out at its
  first checkpoint boundary and at every boundary after it, including the last.
* **The write itself destroyed what it was protecting.** `Path.write_text` truncates the
  target and then fills it. Measured with a real interrupted write: the previous
  checkpoint's 582 bytes became 84,731 bytes of a half-written successor, and
  `Checkpoint.read` raised `JSONDecodeError`. Neither checkpoint survived.

**Today, with the changes in this handoff, a rental interrupted at minute 110 is
recoverable on `cpu` and `mps` for a model small enough to fit the JSON body, and only if
the caller passes `on_checkpoint=lambda c: c.write(path)` — which is still nobody's job.
That last piece is the first command for the next lane.** On `cuda` it is **not run**: this
host has no CUDA device, nothing here has been measured on one, and a resume reproduces a
trajectory only as exactly as its device does.

And one more, found while asking whether the resume property was true: **a resume onto a
different corpus order was accepted in silence.**

## 1. The property S5 rests on: measured, and true, and not enough

`ShardReader`'s docstring claims *"batches order is a pure function of (seed, epoch,
batch_tokens) and the shard set ... which is only sound if asking twice gives the same
answer twice."* Asked five ways on one real shard set (24-row corpus, 17 batches,
`shard_hash=d547dce3a81ceeea`), digesting index + tokens + lengths of every batch:

| question | digest |
| --- | --- |
| seed 7, epoch 0, `bt=4w`, first ask | `0e5b7bd2864f72d6` |
| the same, asked again in the same process | `0e5b7bd2864f72d6` |
| the same, after asking for epoch 1 in between | `0e5b7bd2864f72d6` |
| the same, from a second process | `0e5b7bd2864f72d6` |
| the same, from a third under `PYTHONHASHSEED=1234` | `0e5b7bd2864f72d6` |
| seed 7, epoch 1, `bt=4w` | `faeee9d00caaf4b3` |
| seed 8, epoch 0, `bt=4w` | `61c8a3c0eef76d8a` |
| **seed 7, epoch 0, `bt=4w+1`** | **`011d15855b660101`** |

The property holds. The last row is the problem. **One extra token in the budget leaves the
batch count at 17 and the indices at 0..16 and replaces every batch.** `Position` is
`(epoch, index)`; `Checkpoint` carried `seed` and `schedule` — by its own docstring, "so a
resume against a differently-seeded source is refused rather than silently training on a
different order" — and carried nothing about `batch_tokens` or the shard set, which are the
other two arguments to the same order function.

So `trainer._skip_to`'s check, "did we land on index N", passed. Measured against
unmodified code, on the real `ShardReader` driven through the real `train_ft`:

```
A  uninterrupted        digest=146b673de7492fe3 steps=8
B  killed at the cap    digest=9e9f91033779f404 steps=4 termination=wall_clock_cap position=(epoch=0, index=4)
C1 resume, same bt      digest=146b673de7492fe3 matches_A=True
C2 resume, bt+1         digest=b3cb211e082a6be0 matches_A=False termination=steps_exhausted -- NO REFUSAL
   _skip_to on the wrong source: returned index=4 after skipping 4; identical to the right source's batch 4? False
```

`C2` ran to completion, reported `steps_exhausted`, and produced a loss trajectory that is
not the one it claims to be resuming. The same shape in the test idiom, against the
pre-fix package loaded from `git show HEAD`:

```
qd_train.trainer     -> .../prefix_pkg/qd_train/trainer.py
Checkpoint has consumed_digest? False
a run killed at the cap: index=3
the impostor shares every index: True
  resume onto the impostor -> SUCCEEDED, no refusal. termination='steps_exhausted' steps=10 loss_digest=58fee36f2368238e
  the uninterrupted run it claims to reproduce: loss_digest=856d8ad1ad96adab -> same? False
```

**Fix.** `Checkpoint` carries a required `consumed_digest`: a running sha256 over every
batch the run actually ate, in order (`ConsumedPrefix`, `python/qd_train/run_control.py`).
`_skip_to` rehashes the prefix it walks past and `_train` refuses a mismatch. Enumerating
the order's parameters would have fixed the case; hashing the data fixes the class — a
different budget, a different shard set, a rebucketing, a rewritten corpus, or anything
nobody has thought of yet all land in the same digest. Post-fix, `C1` still reproduces `A`
exactly and `C2` reads:

```
C2 resume, bt+1  REFUSED: the 4 batch(es) before the resume point hash to 32732b86... but the
checkpoint recorded ceaf94c8.... The source is not the one the checkpoint was taken from --
same seed and epoch, different batches.
```

**The limit, stated rather than hidden:** this cannot see a source that is identical up to
the resume point and differs after it. For a shard set that is narrow, because bucket
membership makes the prefix depend on the whole set — but it is a limit, not a proof.

**The cost, measured rather than asserted:** one sha256 per consumed batch, at 2.7–3.0 GB/s
over the batch's own bytes on this host — 0.024 ms for 8x2048, 0.75 ms for 64x8192
(524,288 tokens, 2.10 MB). Under one percent of an H100 optimizer step, and it is paid on
the training path, not only on the resume path.

## 2. What a checkpoint contains, and what it is missing

| field | present | enough to resume? |
| --- | --- | --- |
| `position` (epoch, index) | yes | yes, *given* the order is pinned — see §1 |
| `optimizer_step` | yes | yes |
| `seed` | yes | yes, and checked against the recorder's protocol |
| `schedule` | yes | yes — the LR is recomputed, never restored |
| `loss_log` + `loss_digest` | yes | yes, exactly (`float.hex`) |
| `consumed_digest` | **added this lane** | closes §1 |
| model weights | via opaque `model_state` | **only if the step converts them** — see §3 |
| optimizer state | via opaque `model_state` | same |
| framework RNG state | **was absent everywhere** | see §3 |
| dataloader position | deliberately absent | correct: the order is *rebuilt* from `(epoch, index)`, not restored |

`model_state` is opaque to `run_control` on purpose — that module imports no torch. Opaque
was also unchecked, which is how a state dict of tensors got as far as `write()`.

## 3. Device independence, and the RNG nobody was carrying

`Checkpoint` is JSON. A tensor is not JSON, and a tensor also carries the device it was
trained on. Both problems have one fix: refuse state the checkpoint cannot write, **where
it is built** rather than where it is used. `_refuse_unwritable` walks `model_state` at
construction and names the offending path.

That makes the refusal real, so `Rung0Step` had to become compliant rather than lucky. Its
`state()` now returns plain Python off the accelerator (`_portable`/`_revive` in
`byte_train.py`: every tensor detached, moved to CPU, and written with its dtype and shape
so revival is exact rather than whatever `torch.tensor` infers from a list of floats), and
it carries the framework RNG state, which nothing did before. That matters because
`ByteDeciderConfig.dropout` is configurable and `Rung0Step.accumulate` calls
`model.train()`: with dropout above zero, a resumed run was drawing from a *fresh* random
stream and the loss log would not have said so.

Measured after the change, torch 2.12.1, rung 0 on cpu:

```
write(<file>)            -> ok
file on disk: 2,080,749 bytes for 44,736 parameters
read back: position={'epoch': 0, 'index': 4} optimizer_step=4 consumed_digest=f1c8696e...
next micro-batch loss: original=0.019779132679104805 restored=0.019779132679104805 identical=True
the word 'cuda' appears in the file: False
the word 'mps' appears in the file: False
the word 'device' appears in the file: False
```

A fresh step loaded from the file agrees with the original bit-for-bit on the next
micro-batch, and the file names no device.

**The number in that block is also a finding: 2,080,749 bytes for 44,736 parameters is 46
bytes per parameter.** JSON stores a float as decimal text. At that rate the 2B backbone
this program is built around serialises to roughly **93 GB per checkpoint**, which is not a
slow write, it is a rented hour spent filling a disk. `MAX_CHECKPOINT_BYTES` (1 GiB, about
23M parameters) now refuses it loudly and says what to do instead — model state in a
sidecar tensor file with its digest in the JSON. **Building that sidecar is a design
decision, not something this lane invented at short notice; it is the first real item for
whoever owns the 2xH100 run.**

## 4. Crash safety

The ledger learned this lesson already (`O_APPEND` + `fsync` + `flock`). The checkpoint had
not. `Checkpoint.write` now writes a temporary file in the target's own directory, `fsync`s
it, `replace`s it onto the target, and `fsync`s the directory; a failure removes the
temporary file. A `SIGKILL` mid-write leaves a visible `.tmp-<pid>` beside an intact
checkpoint.

The integrity check grew to match. `loss_digest` covered the loss log and left the weights,
the position, the schedule and the seed unguarded, and it was read with
`raw.get("loss_digest")` and skipped when absent — so deleting one key turned the only check
in the file off. There is now a `payload_digest` over the whole body, and an absent digest
is a refusal rather than a skip.

## 5. Rule 8: `quick` was self-reported, and the evidence was already in the row

Rule 8 says a truncated schedule is `quick` and promotes nothing. `promotion_verdict`
enforces the three-seed half structurally, and took `quick` on trust. A row records
`train.termination`, and `_train` sets it to `wall_clock_cap` when the cap stops the run —
a truncated schedule in rule 8's own words. Measured against the pre-fix ledger: three rows
differing only in seed, every required gate and control passing, one of them honestly
recording `wall_clock_cap`, all three `quick=False`:

```
rows: [(1, False, 'steps_exhausted'), (2, False, 'wall_clock_cap'), (3, False, 'steps_exhausted')]
promote? True
  refused: 3 completed rows, seeds [1, 2, 3], every gate and control ran and passed
```

`promotion_verdict` now derives the refusal from the row instead, and additionally refuses a
`cpt`/`ft`/`prune_heal` row that carries no `train.termination` at all — an absent answer is
not a passed one, the same rule its gates follow. Post-fix the same ledger answers
`promote? False`. This makes promotion **stricter**; no threshold was moved (rule 2).
