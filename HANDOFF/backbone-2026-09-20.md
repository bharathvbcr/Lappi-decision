### The construction decision — measured, not argued

`Qwen3_5TextModel` and `Qwen3_5TextConfig` **exist in transformers 5.12.1**, which settles
the brief's open question. Measured against snapshot `b1485b2f`:

| | count |
| --- | --- |
| `Qwen3_5TextModel(config.text_config)` state_dict entries | 320 |
| checkpoint tensors under `model.language_model.` | 320 |
| keys in one and not the other, either direction | **0** |
| shape mismatches | **0** |

So the key sets are a **bijection**. `load_text_tower` builds the text-only model and loads
exactly those 320 tensors, rather than loading the whole `Qwen3_5ForConditionalGeneration`
and taking `.model.language_model` — which would allocate the vision tower's 331,416,576
and the MTP block's 60,828,160 parameters (785 MB of bf16) in order to discard them. The
bijection is re-checked on every load; a snapshot that differs is refused with both
differences named, because `strict=False` is how a model trains with randomly initialised
layers and a merely disappointing loss curve.

### Gradient checkpointing — it works, and the obvious instrument does not

transformers 5.12.1 implements it in `GradientCheckpointingLayer.__call__`, which
`Qwen3_5DecoderLayer` inherits; `modeling_qwen3_5.py` contains **no
`_gradient_checkpointing_func` call of its own**, and neither do `qwen3` or `qwen3_next`.
That is a mechanism inherited from a base class, so `load_text_tower` reads the flag back
off every decoder layer and refuses when any layer did not take it.

**A forward-count hook is the wrong instrument.** Measured: `register_forward_hook` on each
layer reported 4 forwards and **0 recomputed** in both the ON and OFF states, which reads as
"checkpointing does nothing". `torch.autograd.graph.saved_tensors_hooks` — which counts what
the graph actually retains — showed 32,463,552 B → 724,224 B on the same model. The first
instrument cannot see recomputation; only the second measures the quantity that matters.
`saved_activation_bytes` is that measurement, exposed and tested.

### The memory arithmetic — reproduced, and one figure in the brief corrected

All four cells reproduce exactly from `qd_train.memory` (static bytes, GiB):

| | fp32 master | no fp32 master |
| --- | --- | --- |
| full vocab 248,320 | 28.04 | 21.03 |
| remap vocab 13,787 | 20.88 | **15.66** |

The optimizer-precision choice stays **unmade**: `load_text_tower` takes an `OptimizerSpec`
with **no default**, so every caller states which of the four its budget describes.

> **Correction.** The brief says checkpointing "fits at **8 rows/batch (25.85 GB)**". Those

> does not fit). Both numbers are individually right; they do not go together.

## 2. What was built

**`python/qd_train/backbone.py`** (new, 700 lines) — the canonical owner.

- `text_tensor_index` — the checkpoint's text tensors from the safetensors header, torch-free.
- `load_text_tower` — the bijection check, the load, the checkpointing decision and its
  verification, and a `StepFootprint` bound to the recompute policy actually in force.
  `gradient_checkpointing` and `optimizer` are **required keywords**; there is no default to
  forget. OFF emits `GradientCheckpointingDisabled` carrying the arithmetic, and budgets at
  `recompute="none"` so the 108.15 GB case can never be reported as the 25.85 GB one.
- `_verify_spec_describes` — refuses a `ModelSpec` that describes a different model than the
  one loaded. Without it, any non-2B tower silently received a footprint about the 2B model,
  which in a report is indistinguishable from a budget that was checked.
- `remap_text_tower` — delegates the slice to `qd_train.remap.apply_remap_to_model` (not
  reimplemented) and adds the check that function cannot make: **row contents, in both
  directions, over every kept row**, never a sample.
- `saved_activation_bytes` — the checkpointing measurement.
- `QwenDecisionStep` — a `SpanScoringStep`: the tower's hidden states, `fused_ce` against
  the tied embedding as the head, `SpanPointerHead` for span rows.

**`python/tests/test_backbone.py`** (new, 22 tests, all passing under the torch suite).

**`python/tests/test_schema_mirror.py`** — one line: `qd_train.backbone` added to
`TORCH_GATED`. That test checks both directions, so the declaration is load-bearing.

### Two things that changed my design mid-lane

1. **`state()` must not own a sidecar.** I first had `state()` write its own safetensors
   file and return a path plus sha256. Then I found the SIDECAR lane building exactly that
   inside `Checkpoint`: `TensorRef`, `MAX_SIDECAR_BYTES`, a per-tensor digest on read. Mine
   was a second convention for one thing. `state()` now returns `TensorRef`s and writes
   nothing, and `Checkpoint.write`/`read` round-trips it bit-exactly — verified, as a test,
   against the real `Checkpoint` (14,848-byte JSON body plus one sidecar).
2. **`checkpoint_dir` could not be optional, then became unnecessary.** `trainer._train`
   calls `step.state()` at `trainer.py:805` at the end of **every** run and at `:793` at
   each checkpoint interval — not only when a checkpoint was requested. Converging onto
   `TensorRef` removed the question.
