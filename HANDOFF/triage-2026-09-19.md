## The three findings — records that were WRONG AS STATED

### 1. `GAP-DATA-NETWORK-OFFLINE` — the host is reachable; the probe cannot tell

The record says the dataset host is unreachable. It is not. Measured from the repo venv today:
`https://huggingface.co/api/datasets/bigcode/commitpackft` → **HTTP 200**, body reporting
`"gated": false`; `https://huggingface.co/api/models/Qwen/Qwen3.5-2B-Base` → **HTTP 200**;
`https://pypi.org/simple/` → **HTTP 200**; and a raw TLS handshake to
`datasets-server.huggingface.co:443` completes with a valid peer certificate.

Why the original method reached "unreachable": `python/tests/test_loaders.py:192-201`
`_host_reachable()` probes `https://datasets-server.huggingface.co/valid` and returns `False` on
`except (urllib.error.URLError, TimeoutError, OSError)`. `urllib.error.HTTPError` **is a subclass of
`URLError`** (verified), so any HTTP error status is classified as unreachable — and `/valid` is a
retired endpoint that answers **404** (the current spelling `/is-valid` answers **500**). Running
the test today still prints `SKIPPED … datasets-server unreachable`. The skip is honest that the
test did not run; the *reason* it states is wrong, and the reason is what decides whether anyone
retries.

This is the repo's own defect shape — a check that cannot distinguish two outcomes reporting the
stronger one — and it has propagated. Four other records rest on it and their blockers are wrong:
`GAP-DATA-COMMITPACKFT-LANG-COVERAGE-NOW-FAILS-CLOSED` (the 702k-row `lang` distribution is
measurable today, and the dataset is not gated), `GAP-DATA-LSH-RECALL-BOUND-NOW-STATED-AND-MEASURED`,
`GAP-S4-SPAN-OFFSETS-UNVERIFIED-ON-REAL-TOKENIZER` and `GAP-S4-LINE-STARTS-COLLAPSE-UNDER-BPE`. For
the last two the real blocker is a cached tokenizer, not connectivity: `transformers` 5.12.1 and
`datasets` 5.0.0 import fine from `/Users/bharath/.venvs/ml`, and no `models--Qwen*` exists in
`/Users/bharath/.cache/huggingface/hub`.

Fix: catch `HTTPError` separately and probe an endpoint that exists.

### 2. `GAP-S1-VLLM-INDEX-PRECEDENCE` — the flag does not resolve cleanly, it resolves wrongly

The record's answer is that the plan's single-environment design holds "but only with
`--index-strategy unsafe-best-match`". Three things I verified myself. `stack/requirements.in` and
`stack/requirements.lock`, the two files its workaround names as carrying the flag, **do not exist**

the produced lockfile for internal consistency, which is where the two CUDA families were visible.
The design was split into two lockfiles and two images; README §3a keeps the observation as a named
trap.

### 3. `GAP-GAPS-JSONL-REWRITTEN-NOT-APPENDED` — nothing was lost, but one line was edited

The record says it is unprovable from where it stood whether the whole-file rewrite lost a record.
It is provable, and the answer is **no record was lost**. I reconstructed every committed version
with `git --git-dir=…/.git show <sha>:gaps.jsonl` across all seven commits that touch it —
`4cd4cfa` 6 lines/6 ids, `eb78d34` 15/15, `1149dc8` 16/16, `a3306b3` 123/123, `9e67eff` 170/152,
`337876f` 196/163, `518bf10` 199/164 — and diffed the id set at each step. The set never shrinks.

Why the original method reached "UNPROVEN": it concluded unprovability from tool unavailability,
reporting that `git -C`, `git --git-dir` and `cd` were all blocked. Only `cd` and `git -C` are; an
explicit `--git-dir`/`--work-tree` pair works from this lane, and the history was in the object
store the whole time.

One smaller thing *is* true and is new: the rewrite in `a3306b3` re-emitted sixteen pre-existing
lines, fifteen byte-identical, and **edited `GAP-S1-NO-DOCKER`'s `residual` field in place** (333
characters became 701). That is a history line mutated rather than superseded by an append — the
only one in the file's history. The infrastructure half of the original action stands: `gaps.jsonl`
still has no `O_APPEND` + `fsync` protection, unlike `Ledger.append`.
