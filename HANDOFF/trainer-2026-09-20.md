Three things in that table are worth more than "it ran".

**Both slot losses fall, separately.** A falling total with a flat span term would be a model
that learned the mutation class and nothing about *where*. `Rung0Result` carries both and the
tool prints both; span falls from 5.45 to 6e-7 and choice from 1.55 to 1e-6.

**`mps` is 3.8x SLOWER than `cpu` here.** 51–65 steps/s against 230–245. Expected at this size
— kernel dispatch dominates a 172K-parameter model — and worth stating so the next lane does
not read a Metal number as a capability ceiling. MPS is not on the critical path for rung 0.

**`mps` and `cpu` agree to the printed precision on every seed**, which is a stronger statement
about the path than either arm alone.

### The loss stops where the data says, not where the model gives up

The first version of the toy corpus reused one function body across every mutated row while
cycling the gold class, so four rows carried identical bytes and three different labels. The
choice loss stopped at **0.5199** on all three seeds and did not move. The corpus's conditional
label entropy, computed independently, is **0.519860**. The head was right; the data was
unlearnable. A plateau invites the opposite reading, so the tool now computes the floor
(`_choice_floor`) and asserts against it rather than merely asserting the loss fell. On the
corrected corpus the floor is 0.0 and all six runs reach it.

This is why the metric in the ledger is `choice_loss_reached_its_floor` and not `loss_fell`: a
head pointed at the wrong column can produce a falling curve, but it cannot reach that number.

## 3. The heads, in integers

Run on every invocation of the tool and printed under `wiring`.

**Choice — a maximal slot is 17 rows and the abstention is last.**
`ByteDecider` with `n_live_options = 16` returns width **17**, selectable columns
`[0..16]` — all 17, none dead — and `abstain_column(16) == 16`, the last. Against
`schema.rs:19 MAX_OPTIONS = 16` plus `schema.rs:112 RESERVED_NOUL_ROWS = 1` = 17. Anything
asserting a 16-row total is wrong, and nothing in `python/qd_train/` does.

**Span — abstention last, per context, not at the padded width.**
A 3-line context gives `span_head_rows(3) == 4`, `SpanPlan.runtime_rows == 4`, and an
abstaining row's gold at row **3** — the last. Against `answer.rs:70`
`span_rows = line_count + RESERVED_NOUL_ROWS` and `noul_row = plan.rows - RESERVED_NOUL_ROWS`
at `answer.rs:303, 366, 398, 482`.

**Score — ordinal in the row count only.** `schema.rs:196` sizes a score slot at
`bins + RESERVED_NOUL_ROWS`, which is right. But `docs/schema-api.md:107` says the loss is
"cumulative (CORAL-style)" and **no such loss exists on either side**. Every occurrence of
"CORAL" in the repository is prose. `trainer.ft_supervision` splits out only `SLOT_SPAN` and
routes `SLOT_SCORE` through the same letter channel as `SLOT_CHOICE` with plain cross-entropy;
`answer.rs`'s `Score` arm uses `QueryKind::Letters` and an argmax, the same decode a choice
slot gets. Recorded as `GAP-TRAINER-SCORE-SLOT-HAS-NO-ORDINAL-LOSS`; **decide before a score
slot is trained**, because adding the cumulative loss afterwards changes the objective and the
checkpoints are not comparable across the change.

### The dangerous half of `GAP-SCHEMA-NOUL-LETTER-BUDGET`, demonstrated

That record's residual said the POSITION was verified on the Rust side only, because
`test_heads.py` `importorskip`s torch. **Run under `/Users/bharath/.venvs/ml`: 140 passed, 0
skipped** across the six torch-gated files, including
`test_the_abstain_row_is_last_as_the_runtime_reads_it`. The residual closes.

The tool then builds the defect on purpose. Two span heads, same data, same 60 steps, same
seed; one trained with the abstain gold on the reserved last row, one on row 0. Both read the
way `answer.rs` reads them:

| trained with abstain at | final loss | argmax row | what the runtime answers |
| --- | --- | --- | --- |
| row 4 (last — as shipped) | 1.43e-06 | 4 | **abstain** |
| row 0 (the defect) | **0.0** | 0 | **line ordinal 0** |

The defective layout reaches a *better* floor. Every no-evidence answer lands on the first line
of the context, and no loss curve says so. That is the whole content of the residual, measured
rather than argued, and the shipped code is on the correct side of it.

## 4. Two things that succeeded where they should have refused — both fixed

### 4.1 Rung 0's training data had no rule-3 door

`GAP-TRAINER-RUNG0-DATA-DOOR-UNGUARDED`. Measured against unmodified code:

```
data/heldout/mutate.jsonl
  data_access.assert_path_not_held_out -> REFUSES: HeldOutViolation
  mutate_adapter.read_examples         -> ADMITS: 1 example parsed, 1 trainable ByteDecision
```

CLAUDE.md rule 3 says "a path check in `qd-train` refuses them". The S4 path carries it twice —
`open_training_data` for the manifest, and `artifacts.assert_shard_trainable` for the shard,
the second added because *"without this the held-out check is satisfied on paper and bypassed
by indirection"*. Rung 0 reads a qd-mutate JSONL directly and went through neither.
`read_examples` took no `config` and no `repo_root`, so it could not have checked.

**Fixed at the canonical owner.** `read_examples(path, *, config, repo_root)` now calls
`data_access.assert_path_not_held_out` before opening the file — the same function the other
two doors call, not a second implementation of the rule. Both arguments are required: an
optional check defaults to off.

Five new tests in `test_mutate_adapter.py`, plus a control that admits an ordinary corpus under
the same config. Mutation **M1** — guard removed, signature unchanged, so the kill is not a
`TypeError` — fails all five refusals and leaves the control passing.

### 4.2 The ledger row said `mps` for runs that happened on `cpu`

`GAP-LEDGER-ENV-DEVICE-WAS-THE-HOST-NOT-THE-RUN`. `Environment.detect()` answered
`torch.backends.mps.is_available()`, which is a fact about the *host* and identical for every
run on it. The first six rows this lane wrote — three on `mps`, three on `cpu` — **all say
`mps`**. A device comparison was unfalsifiable from the ledger alone.

**Fixed at the canonical owner.** `Environment.detect(*, transformers_sha, device=None)`: a
caller that chose a device says so and it is carried verbatim; `None` still auto-detects, which
is correct for `record_build_run`, whose row should carry what the host is because it never
chose.

`detect` has two branches and the repo venv, having no torch, takes only the `ImportError` one,
so each was mutated separately. **M2** (try branch ignores the parameter) kills two of the three
tests under the ml venv with `assert mps == cpu` — the original defect exactly. **M3**
(`ImportError` branch ignores it) kills the first under the repo venv. `test_ledger.py`: 63
passed under both venvs after restoring.

**The three wrong rows stand.** The ledger is append-only. `f319e417-2be0-49d2-a492-ffb86e17dda0`,
`98d4f2a2-347c-462f-b635-449d871251df` and `4216e8b2-578b-427a-bf9d-4c4ca5e0817b` are `cpu`
runs whose `env.device` says `mps`; they are superseded by the six rows in section 2 and the
gap record names them.

## 6. Rule 4: the GPU job is the next step, and this lane stops here

Nothing was launched on rented hardware and nothing should be until a human says so. What this
lane establishes for that decision:

* The **rung 0** path executes, converges and writes rows. It does not need a GPU at all — CPU
  is the faster device at this size — so **rung 0 is not a reason to rent anything.**
* The **S4 / 2B** path (`trainer.train_cpt` / `train_ft`, `shards.ShardReader`, `remap`,
  `fused_ce`) is **NOT RUN.** It has no entry point, and no run of it exists on this host. Its
  tests pass under the ml venv; that is a statement about the code, not about a training run.
* `RunControl` already refuses to start a run whose `CostEstimate.requires_human_approval` is
  true without `approved_by` — multi-GPU always, single-GPU once the capped cost reaches $20.
  That mechanism works and is the right place for rule 4. It has never been exercised against a
  real rate, because no run has ever had one.

**Recommendation to the coordinator:** before any 8xH100 launch, the S4 path needs the same
treatment this lane gave rung 0 — a toy run that proves `train_ft` executes, that its loss
falls on a memorisable batch, and that its letter channel puts the abstention where
`answer.rs` reads it. That can be done on this Mac with a randomly-initialised small config and
costs nothing. Spending 8xH100 hours to discover a wiring bug that a 30-second CPU run would
have caught is the failure this lane was set up to prevent, one rung up.
