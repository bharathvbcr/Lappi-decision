# GH200 lane — 2026-09-20

**The question this lane owns: does any of this run on a real GPU?** Before today nothing in
this repository had ever constructed the real model, and no ledger row had ever been written
from a CUDA device. A GH200 (96 GB HBM3, aarch64 Grace, sm_90) was rented at $2.20/hr and the
answer is **yes, with one hard blocker and six defects that only a real box could surface.**

Nothing was committed. The rented box was set up, used, and left running; every number below
cites a command that was run.

---

## 1. The environment, which behaved exactly as predicted

`tools/verify_lock_portability.py --platform aarch64-manylinux_2_28` said **portable to
aarch64** before a box existed: 71 `train.lock` pins and 196 `teacher.lock` pins resolving
identically to the committed x86_64 lock, the `torch 2.10.0+cu128` cp312 aarch64 wheel
present, 2 causal-conv1d aarch64 wheels present, and the other 69 PyPI pins `match=30,
pure=39` with zero blocking and zero unanswered.

Measured on the box, and the prediction held in every particular:

| | |
| --- | --- |
| host | `aarch64`, 64 vCPU, 525 GiB RAM, 3.9 TB disk |
| GPU | NVIDIA GH200 480GB, **94.50 GiB** visible to torch, sm_90, driver 580.105.08 |
| CUDA | 12.8 — the version `torch==2.10.0+cu128` targets |
| install | `uv pip install -r stack/train.lock` into a 3.12.14 venv, **7m07s**, no failures |
| causal-conv1d | **1.7.0 with its compiled `causal_conv1d_cuda` extension** |

That last row is the one worth dwelling on. `stack/README.md` calls the from-source
causal-conv1d build *"the single most fragile step in the image"* — memory-hungry enough to
invite the OOM killer and unable to build under emulation at all. It did not happen: the
prebuilt aarch64 wheel was found and used, exactly as the portability check predicted.

**`stack/README.md`'s "aarch64 image **not needed** — GH200 is the only aarch64 target and is
out of capacity" was corrected** to "needed, NOT BUILT", carrying the measurement above. No
image was built: the environment was installed directly with `uv`, which is faster than
shipping 17.4 GB and is what the next lane should do too until an image earns its keep.

## 2. The blocker: the fast path refuses on Hopper

```
RuntimeError: Triton >= 3.4.0 and < 3.7.1 on Hopper GPUs produces incorrect results for
gated chunk_bwd_dqkwg (see #640). Please upgrade Triton to >= 3.7.1 or install tilelang
```

`flash-linear-attention` **refuses the GDN backward** on this device. The pins are a vise:
`importlib.metadata.requires("torch")` for `torch==2.10.0+cu128` returns
`['triton==3.6.0; platform_system == "Linux"']` — an **equality**, not a floor. So on Hopper
the lock's triton and fla's requirement cannot both be satisfied.

**The guard is what saved the run.** Without fla's version check, triton 3.6.0 on Hopper would
have computed `chunk_bwd_dqkwg` incorrectly and returned it: a run that looks healthy, loses
loss, and learns from wrong gradients. Nothing on a Mac and nothing in the x86 image could
have found this — the forward works, the install works, every gate is green, and only the
backward on this hardware fails.

Recorded as `GAP-STACK-FLA-REFUSES-ON-HOPPER-WITH-THE-PINNED-TRITON`, **open**. The three
options — stay on the reference PyTorch path, add `tilelang` (a new dependency, not taken), or
move the torch pin (which reopens the causal-conv1d prebuilt-wheel question that pinning torch
to 2.10 exists to settle) — are the human's, and the throughput cost of the reference path is
**not yet quantified** because the fast path cannot run here to be compared against.

One trap for whoever acts on this: uninstalling `flash-linear-attention` does **not** remove
the code. The importable `fla` package is owned by the **`fla-core`** distribution, so the
lock's named package can be removed while `import fla` keeps working.

## 3. Six defects, each found by running rather than reading

Every one was invisible to `make gates`, which was green throughout.

**1. `tools/real_ft_run.py` had no CUDA branch at all.** `devices = ["cpu"] + (["mps"] if
torch.backends.mps.is_available() else [])`. Written on a Mac, so a rented GPU box would have
trained on the CPU without saying so. `cuda` now joins on the same tri-state terms `mps` is
already on, and `--devices` overrides.

**2. `fla_present` and `causal_conv1d_present` were never set by anything.** The only
assignments to either field in the whole repository were `ledger.py`'s own JSON parser reading
a row back, and test fixtures. So every row ever written carried the dataclass default —
`"fla dry run not executed"` — whether the package was present, absent, used or refused, and a
fast-path run and a fallback run produced byte-identical environment records. `Environment.detect`
now probes both. On this box it writes:

> `fla 0.5.2 is importable but REFUSES on this device: triton 3.6.0 on Hopper computes
> chunk_bwd_dqkwg incorrectly (fla raises for triton in [3.4.0, 3.7.1)). Any run here used the
> reference PyTorch path, not this kernel.`

`passed` stays literal — the field is named `present` and answers presence — and usability
goes in the detail, because present and usable are two quantities.

**3. The remap refused a padded embedding.** `the model's input embedding has 248320 rows but
the remap was built over a 248077-token vocabulary ... the wrong tokenizer`. Both numbers were
right and nothing was wrong: the tokenizer is 248,044 base + 33 added = **248,077**, and the
embedding is **248,320 = 1940 × 128**, aligned for tensor cores. Rows 248,077–248,319 are
unreachable and `index_select` never selects them. The check was `!=` where the invariant is
directional — smaller is fatal, larger is padding — and it now also checks the highest kept id
directly, which catches a remap whose `new_to_old` exceeds its own declared `source_vocab_size`
and which no size comparison can catch. Three tests in `test_remap_torch.py`; the existing
`test_a_remap_for_a_different_vocabulary_is_refused` was left untouched by keeping its
contract phrase in the new message.

**4. The two step classes had drifted in two places**, exactly as
`HANDOFF/backbone-2026-09-20.md` warned. `RealFtStep.hidden(tokens: np.ndarray)` against
`QwenDecisionStep.hidden(batch: Batch)`, and `lm_head` existing only on the stand-in. Neither
is named by `SpanScoringStep`, so nothing type-checked them and both failed at runtime on the
box. Unified on `Batch` — the richer interface, because the real tower needs `batch.lengths`
for its attention mask and a bare array cannot supply it — and `QwenDecisionStep.lm_head` added
over the tied embedding.

**5. `SpanPointerHead` did not own its dtype.** It is float32 by construction so the pointer
logsumexp is not computed with 8 bits of mantissa; a real tower emits bf16. `accumulate_span`
cast, and `real_ft_run._evaluate` reaches past the step into `span_head.loss(...)` directly and
did not — `RuntimeError: expected mat1 and mat2 to have the same dtype`. `forward` now casts,
so a new call site cannot get it wrong.

**6. The tool's defaults are the stand-in's defaults.** `--lr` defaults to `3e-3`, which is
right for a randomly-initialised 128-wide block and high enough to destroy pretrained weights.
Driven at the default, the run completed and failed its own floor checks with a span-channel
gap of **714.50** against a bar of 0.05 — what a wrecked model looks like, which is easy to
mistake for a loop bug. Worse, `--hidden` and `--heads` are silently **ignored** under
`--real-backbone` (the real tower's width and head count come from `config.json`) while still
being written into `recipe` — and `recipe` feeds `recipe_hash`, so two bit-identical runs
differing only in `--hidden` get different protocol hashes. Recorded, **not fixed**:
`GAP-TOOLS-REAL-FT-DEFAULTS-ARE-THE-STAND-INS-DEFAULTS`.

## 4. What the real model actually did

Loaded from the snapshot whose hash is the `backbone_commit` in the ledger rows
(`b1485b2fa6dfa1287294f269f5fb618e03d52d7c`), downloaded on the box in 17s, 4.57 GB:

- **320/320 tensors**, exactly **1,881,825,088** parameters, matching the independent
  safetensors-header inventory;
- gradient checkpointing on, retained activations **3,334,717,056 B → 7,348,992 B**;
- the tied embedding remapped 248,320 → **14,016** rows, both directions verified over every
  kept row.

Backbone-only throughput, synthetic ids, rows=1, reference PyTorch GDN path:

| width | s/step | tok/s | peak |
| --- | --- | --- | --- |
| 2048 | 1.45 | 1412 | 17.60 GiB |
| 4096 | 2.60 | 1575 | 17.60 GiB |
| 8192 | 5.14 | 1594 | 17.62 GiB |

Peak is **flat across a 4× width range** — gradient checkpointing doing exactly its job — with
76.9 GiB spare on a 94.50 GiB card.

And on the real shard set, one forward+backward per bucket in a subprocess, **all eight
buckets pass on cuda including bucket 7 at `1 × 34,522` in 1.613s**. That closes the question
the MEMORY lane could only answer arithmetically: the widest real bucket trains.

### It trains, and it reaches the floor

40 passes over 10 of 111 real batches (128 of 341 sequences), one seed, `--lr 1e-5`, cuda:

| channel | first | last | floor |
| --- | --- | --- | --- |
| letter | 2.195080518722534 | **5.7220458984375e-06** | 0.0 |
| span | 437.22467041015625 | **5.0734757678583264e-05** | 0.0 |

**1729.353 s wall clock — 28.8 minutes, $1.06 at $2.20/hr.** Ledger rows
`739f6035-f549-48e9-b51a-0154ad5daca3` (ft) and `42974d92-fd23-4765-ac11-f5e9317129af`
(verdict), both `quick=True`, `device=cuda`. The tool exits 0: both floor claims held.

The same run at the tool's default `--lr 3e-3` failed them, with a letter gap of 3.96 and a
span gap of **714.50**. The difference between those two runs is one flag, and nothing in the
tool warns about it.

**The optimizer arithmetic is overstated.** `torch.optim.AdamW` over bf16 parameters keeps its
moments in the parameter dtype and holds no master copy — **8 B/param, 14.02 GiB** — against
`memory.py`'s `ADAMW_FP32` 16 B/param (28.04 GiB) and no-master 12 B/param (21.03 GiB). The
arithmetic describes what one **should** do; 8 B/param is what one **gets by accident**, and
bf16 Adam moments lose precision in exactly the way that quietly degrades a long run. This is a
recipe decision and it is still unmade.

## 6. The ledger forked across two machines, and nothing can see it

`docs/ledger-schema.md:250` covers concurrent writers to **one file** with an exclusive
`flock`, because without it two processes read the same `last_line_hash` and the chain refuses
from that line onward permanently. That remedy is within-machine and does not reach across
machines: rsync made a second copy with a common prefix, both sides appended, and the two are
now divergent chains sharing an ancestor — **162 rows on the box, 157 here**.

Both verify independently. That is exactly why it is quiet: neither side's `ledger verify`
reports anything, and `make gates` stays green on both. Concatenating them is worse than
useless — every row after the divergence names a predecessor that is no longer its
predecessor, which is the same permanent refusal the flock exists to prevent, reached by a
route the flock cannot see.

Recorded as `GAP-LEDGER-NO-STORY-FOR-A-CHAIN-FORKED-ACROSS-TWO-MACHINES`, **open**. The box's
ledger is kept as its own file rather than merged, so its rows keep the hashes they were
written with.
