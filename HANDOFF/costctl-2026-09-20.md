# COSTCTL lane — 2026-09-20

**Subject:** `python/qd_train/run_control.py` — the wall-clock cap, the auto-terminate, the
cost estimate and the approval threshold rule 4 depends on. The human is about to rent
**2x H100 80GB SXM5 at $8.38/hr per instance, $4.19/GPU/hr**.

**The headline:** rule 4 names four things. Three were enforced by the type. The fourth —
**auto-terminate — was not enforced anywhere, and did not exist.** `expired()` is a *poll* a
cooperative loop makes at optimizer-step boundaries. Measured: a step that blocked ran **60x
past a cap** with `expired()` answering `True` to nobody, the process still running and
`cost_so_far()` climbing at $22.32/h. A second finding of the same shape: a clock that
stepped backwards **silently extended the cap and lowered the recorded bill**, because
`max(0.0, clock() - t0)` turned the regression into a zero.

Nothing was launched. No GPU was rented. Nothing was committed.

## 2. What broke

Seven findings. Five are fixed here; two are reported and **not** fixed, with reasons.

### 2.1 Rule 4's auto-terminate did not exist — **FIXED**

`RunControl` had no `stop`, `terminate`, `kill`, `abort` or `watch` member of any kind.
Measured, pre-fix, on an 8x A100 80GB at $22.32/h with a 0.05 s cap and a step that sleeps:

```
[1] Can a rule-4 run be configured with NOTHING that terminates it?
    RunControl(...) built. terminate members: []
    -> YES. Rule 4 names four things; this run carries three.

[2] The hung step: sleep past the cap, never call expired().
    threads armed by start(): 0
    the step ran 3.00s against a 0.05s cap (60x).
    nothing fired. The process is still running and still billing.
    expired() says True -- to nobody, because nobody asked.
    cost_so_far() = $0.0186 and climbing, at $22.32/h.
    -> the cap is ADVISORY. It bounds a cooperative loop and nothing else.
```

Post-fix, same scenario, same script:

```
[1] REFUSED: LaunchRefused: rule 4: this run needs auto-terminate and has none. […]
    -> NO. Rule 4's fourth requirement is enforced at configuration.
[2] threads armed by start(): 1
    the step ran 0.05s against a 0.05s cap (1x).
    TERMINATED after 0.05s. […]
    -> the cap stopped the run WITHOUT the loop's cooperation.
```

**The fix.** `RunControl` gains `auto_terminate: Callable[[str], None] | None`. For exactly
the runs rule 4 gates — `cost.requires_human_approval` — it is **mandatory**, refused at
construction with `LaunchRefused` like the other three requirements. `start()` arms a daemon
watchdog thread; `stop()` and `__exit__` disarm it. The watchdog is measured against the
**injected** clock, so a test with a frozen clock arms one that never fires on the wall, and a
real run measures real time. A watchdog that cannot *read* the clock fires rather than going
quiet — a check that could not run must not report what a check that ran reports.

`hard_exit_on_cap` is the ready-made action, with a bounded three-rung ladder, each rung
covering the previous one's failure: `interrupt_main()` so a cooperative loop unwinds and
checkpoints → `SIGTERM` for a main thread blocked inside a C call → `os._exit(124)` for a
process that ignores `SIGTERM`. Each wait is `TERMINATE_GRACE_S`; total worst case from
expiry to death is two of them. 124 is GNU `timeout`'s convention and deliberately **not** 3,
which this repo's gates mean by `NotRun`.

**A run that rule 4 does not gate arms nothing** — no terminate action, no thread, no
behaviour added. Pinned by `test_a_run_with_no_auto_terminate_arms_no_thread`.

### 2.2 A clock that steps backwards silently extended the cap — **FIXED**

`elapsed_s()` was `max(0.0, self.clock() - self._t0)`. The docstring said the default
`time.monotonic` is why a backward step cannot happen — but `clock` is an injectable field,
so the default is an argument, not a guarantee. Measured, stepping the clock back 109 s:

```
t=1009 elapsed=9.0  expired=False cost=$0.010725
t= 900 elapsed=0.0  expired=False cost=$0.000000     <- the recorded bill went DOWN
t=1009 elapsed=9.0  expired=False
t=1011 elapsed=11.0 expired=True                      <- the cap fired 109 s of clock-time late
```

`trainer.py:713` feeds `control.elapsed_s()` straight into the ledger row's `cost_usd`, so
this is a wrong number in an append-only file as well as a longer rental.

**The fix.** The reading is validated and the high-water mark is kept; a regression raises
`RuntimeError` naming NTP and DST. A clock that merely *stalls* is not a regression and still
reports — pinned separately so the fix does not over-reach. A lock guards the high-water mark
because the watchdog thread and the loop both read the clock, and two perfectly monotonic
readings can otherwise interleave into a false regression.

### 2.3 A NaN clock made the cap unreachable and the cost $0 — **FIXED**

The `nan > threshold` shape, laundered through `max`: `max(0.0, nan)` is `0.0`, because
Python's `max` keeps the first argument when the comparison is False. Measured:

```
elapsed_s()   with a NaN clock -> 0.0
expired()     with a NaN clock -> False
cost_so_far() with a NaN clock -> 0.0
```

— for as long as the clock stayed broken. This was the **only** place in the module where a
float reached a comparison without `_require_finite`. Fixed at the same site; a clock that
breaks mid-run is refused at the reading rather than swallowed.

### 2.4 A negative elapsed produced a negative bill — **FIXED**

`_require_finite` allowed negatives. Measured: `cost_for(-3600.0)` → `-4.29`;
`cost_for(-1e9)` → `-1191666.67`; `remaining_s(-1e9)` → `1000000010.0` seconds of headroom
against a 10 s cap. A negative elapsed is not a cheap run; it is a broken clock. New
`_require_elapsed` refuses it in `WallClockCap.expired`, `WallClockCap.remaining_s` and
`CostEstimate.cost_for`.

### 2.5 `instance` defaulted to `"unspecified"`, and its own guard accepted that — **FIXED**

The check rejected `""` and `"  "` with a message about *"a rate read off the wrong row"* of
a price list, and then let the placeholder its own signature supplied sail through. Measured:

```
CostEstimate(usd_per_hour=22.32, cap=2h, n_gpus=8).approval_line()
  -> 'unspecified: 8 GPU(s) at $22.32/h, capped at 2.00 h -> $44.64 at the cap -- NEEDS A HUMAN YES'
```

`instance` is now required. `None` is refused with the module's own message rather than an
`AttributeError` from `.strip()`.

### 2.6 The approval line printed a number contradicting its own verdict — **FIXED**

`:.2f` rounds to nearest, so the printed projection and the decision came from different
numbers. Measured:

```
true rate $9.9999/h, true projected $19.9998
  prints: probe: 1 GPU(s) at $10.00/h, capped at 2.00 h -> $20.00 at the cap -- no approval required
true rate $0.004/h
  prints: probe: 1 GPU(s) at $0.00/h,  capped at 2.00 h -> $0.01  at the cap -- no approval required
```

`$20.00 … no approval required` on one line is a lie told in two hundredths of a cent, and the
human approves against the line. A rate of `$0.00/h` reads as a machine that is free. Two new
helpers: `_usd` falls back to exact `repr` when the rounded rendering would land on the other
side of `APPROVAL_FREE_USD`, and `_no_false_zero` (used for dollars **and** for cap hours,
where a 10 s cap printed as `0.00 h`) falls back when a real quantity would render as nothing.
`repr` and not `%g`: six significant figures turn `19.999999998` back into `20`.

### 2.7 Per-GPU vs per-instance rate — **PARTLY FIXED, and the remainder is reported**

`CostEstimate` had **no concept of which column a rate came from**, and — answering the
coordinator's question directly — **`n_gpus` was never multiplied into `projected_usd` or
`cost_for` at all.** It was stored and used for exactly one thing: the `> 1` test in
`requires_human_approval`. Whatever number you typed was the number multiplied by the cap.
Measured, pre-fix:

```
8x A100 80GB: per-node $22.32/h -> $44.64 at a 2 h cap
8x A100 80GB: per-GPU   $2.79/h ->  $5.58 at a 2 h cap (8x under)
   and both say approval=True/True, so nothing distinguishes them
   line: 8x A100 80GB: 8 GPU(s) at $2.79/h, capped at 2.00 h -> $5.58 at the cap -- NEEDS A HUMAN YES
```

**The fix.** At `n_gpus > 1` an estimate must state **both** columns and they must agree
(`usd_per_hour == usd_per_gpu_hour * n_gpus`, within float representation slack). That is the
one check that catches a swap without a price table, because a swap is precisely what makes
them disagree — no threshold invented, and `APPROVAL_FREE_USD` untouched. At `n_gpus <= 1` the
columns are the same number by definition and nothing is required. The approval line now names
the unit and prints both rates.

**What it does not catch, stated rather than hidden.** An estimate that *understates* the GPU
count passes every check, because at `n_gpus=1` the columns agree trivially. That is the shape
that changes the **decision** rather than only the number, and it is pinned deliberately in
`test_what_the_column_check_cannot_catch_is_a_falsified_gpu_count`:

- real 8x A100 40GB, 2 h cap: $15.92/h × 2 = **$31.84 → needs a human yes**
- its per-GPU column declared as one GPU: $1.99/h × 2 = **$3.98 → approval-free**

The window in which the error flips the decision rather than only the number, at a 2 h cap and
a declared single GPU, is a true instance rate in **[$10.00/h, $20.00/h)**.
`GAP-COSTCTL-NGPUS-IS-TAKEN-ON-TRUST`.

**On the live 2x H100 target specifically:** the 2x error does **not** change the decision,
because `n_gpus > 1` forces a human yes either way. What it changes is the number the human
approves against — **$16.76 against $8.38**. Now refused.

## 3. What is reported and NOT fixed

1. **`approved_by` accepts anything non-blank.** Measured: `' x '` and `'an agent said ok'`
   both configure an 8-GPU run. The docstring says *"An agent cannot supply this on a human's
   behalf"*; nothing enforces it and nothing in this process can. It is a recorded yes, not a
   verified one.
2. **`ledger.py:651` has a second, independent copy of the cost arithmetic**, with
   `cost_usd_per_hour: float = 0.0` — a rate that **defaults to zero** — and `ledger.py:769`
   `cost_usd = self.cost_usd_per_hour * wall / 3600.0`. That is the "missing rate silently
   becomes $0" shape that `CostEstimate` is immune to, sitting one file away, and it is a
   second owner of a formula that should have one. Outside this lane's scope; **named for the
   next lane.**
3. **Rule 2 held throughout.** `APPROVAL_FREE_USD = 20.0` and `MAX_CAP_S = 144000.0` are
   byte-for-byte unchanged. I do not believe either is mis-set: $20 is the rule's own number,
   and 40 h is DESIGN-4's. Nothing in this lane moved, relaxed or routed around either.
4. **Nothing in this repository can use more than one GPU** (verified by the coordinator: no
   DDP, FSDP, torchrun, `init_process_group` or `world_size`; `accelerate` declared and never
   imported). On the 2x H100 target, half of $8.38/h buys capacity no code path here reaches —
   **$8.38 of a $16.76 two-hour rental**. `run_control` cannot express "GPUs rented" against
   "GPUs this run can use", so the estimate cannot show it. Recorded in
   `GAP-COSTCTL-NGPUS-IS-TAKEN-ON-TRUST`; whether `CostEstimate` should carry `usable_gpus` is
   a design call left to a human.

## Would I trust this code with the human's credit card?

**Now, for a bounded single rental, yes — with two conditions stated plainly.**

Before this lane: **no.** The cap was advisory. A wedged dataloader would have billed until a
human noticed, a clock step would have extended the cap and lowered the recorded bill, an
unnamed instance printed a rate nobody could check against a price list, and the number on the
approval line could contradict the verdict on the same line.

The two conditions:

1. **`approved_by` is a recorded yes, not a verified one**, and `n_gpus` is taken on trust.
   Both are outside what code can check. The launch line must be read by the human, not just
   produced.
2. **The auto-terminate ladder's last two rungs have not been run.**
   `interrupt_main → SIGTERM → os._exit(124)` is asserted at source level only, because
   running rungs 2 and 3 means killing the process under test. Rung 1 — the watchdog firing on
   a blocked step without the loop's cooperation — **is** measured end to end. Rule 5:
   **rungs 2 and 3 are NOT RUN**, for that reason, and are not reported as passed. They are
   worth one deliberate manual exercise against a throwaway process before the rental.

**Nothing was launched, nothing was rented, nothing was committed.**
