## The split-result cache question (asked by the lead)

*Is the ~202 s rebuild's output deterministic and serializable, and what would key it?*

**Measured** [V, `AUDIT/v6-startup-2026-10-04/split_cache_probe.py`, runs `probe1` and
`probe2` on the v5 argv; their lines are in `AUDIT/v6-startup-2026-10-04/probe-runs.txt`]:

| What | probe1 | probe2 (another process) |
|---|---|---|
| `ft_split_rows` | 200.1 s; train 487,407 rows, val 22,393; peak RSS 26.0 GiB | 203.5 s; same counts; 26.5 GiB |
| canonical digest: `row_id` + `row_content_hash` per row, in order, all 509,800 rows | `fce63f47…e3bf3`, 7.8 s | **the same**, 7.6 s |
| `pickle.dumps`, protocol 5 | 1,707,290,395 bytes (1.59 GiB), 11.6 s, sha256 `0e1a955f…b012` | **the same bytes and sha256**, 12.5 s |
| write + fsync | 0.2 s | 0.1 s |
| read + `pickle.loads` | 0.1 + 9.3 s | 0.1 + 9.4 s |
| loaded rows == rebuilt rows | True | True |
| val rows against the build's own `data/pool/val.json` content hashes | 22,393 of 22,393 equal, 0.3 s | the same |

Both processes ran with Python's string-hash randomisation on (`PYTHONHASHSEED` unset,
`sys.flags.hash_randomization` 1), so their hash seeds differed.

**Answer.** Yes on all three counts. The cache beats the port for every startup after the
first.
- **Deterministic.** Two processes with different hash seeds produced byte-identical
  pickles (`0e1a955f…`) and the same per-row digest.
- **Serializable, with no live objects.** The result is `(train, val)`: 509,800 frozen,
  slotted `DataRow` dataclasses of plain data (`str`, tuples, a `dict`, `Request`,
  `GoldAnswer`). `native_minhash`'s `id()`-keyed tables die with its block. It pickles to
  1.59 GiB, loads back equal in 9.3 s, and is checkable against the build's own manifest in
  0.3 s.
- **What keys it.** Not `data_snapshot_hash` alone: that names the BUILD's output. The
  rebuild is "this code's reconstruction at `--rev`", and code drift is exactly what
  GAP-SHARD-SET-GOES-STALE-AGAINST-THE-CORPUS-CODE-THAT-REPRODUCES-ITS-LABELS is about. A key
  without the code would hand old rows to new code and hide the drift the pairing checks
  exist to catch. The key is a sha256 over:
  - the schema, Python's minor version and the pickle protocol;
  - the scalar arguments of `ft_split_rows`: full `--rev`, `max_pairs`, the row caps and the
    flags;
  - every input file's content sha256: the corpora (~1.5 GB, ~1 s [I, not timed]), the
    general record, the decision pool, the pre-dedupe drops, the exclusion list and its
    attestation;
  - `DataConfig().fingerprint()`;
  - `qd_data.fingerprint.code_fingerprint` (the whole package, by source bytes);
  - the source sha256 of `tools/real_ft_run.py`, `tools/real_tokenizer_pipeline.py` and every
    `python/qd_train/*.py`;
  - the sha256 of the `QD_PREP_BIN` binary.
- **On a hit:**
  - the entry's sha256 is checked against its sidecar before `pickle.loads`;
  - the val rows are checked against the shard set's own `data/pool/val.json` content hashes.
    That check is independent of the key: 0.3 s, and it ties the rows to this shard set's
    build;
  - the log line says the rows were READ FROM the split cache, NOT rebuilt by this run.
- **Expected hit cost** [I: the parts are measured, the sum is not]: key ~1 s + entry sha ~1
  s + loads 9.3 s + check 0.3 s ≈ 12 s, against 200 s on the Mac. That saves ~188 s per
  startup; ~300 s on the box, scaled by the 1.6× CPU ratio.
- **Scope.** One full rebuild per box per corpus and code serves every later startup of every
  seed and lane: train+score, the needle control, each trajectory plan.
- **Where the port still matters.** The first startup per corpus, and the shard build, which
  runs the same code. That is ~200 s once per box, not per call.
- **Recommendation:**
  - the result cache first: opt-in, Python orchestration in `tools/real_ft_run.py`, no
    `qd_data` edit, no Rust, with a fail-first test and an interleaved A/B;
  - the `_escape`/`shingle`/`exact_jaccard` port only if the first-startup cost still
    matters after it;
  - pickle runs code on load: accepted for a same-user local directory, and the sidecar sha
    is checked first.
- **The port's scope.** If it is built, the target includes dedupe's `exact_jaccard`.
  `dedupe` reaches it as a module global (`qd_data/dedupe.py:73,423`), so the
  `native_minhash` seam can replace it, as it does `candidate_pairs`. The earlier ~90 s
  estimate left it out without a reason. With it, the target is ~135 s of the 202 s, as the
  lead said.

## The split-result cache: `--split-cache DIR` (built; opt-in; on `v6-startup` only)

The lead said go, with seven conditions that are part of the go. Nothing here merges or
reaches the box; the human decides. Where the code lives:
- `tools/split_cache.py` (new): the key, the checks, the atomic store, the load, eviction. It
  imports no torch, so it is testable on its own.
- `tools/real_ft_run.py`: the orchestration — the flag, the call, the metric, and
  `split_rebuild_inputs`, which names what the rebuild reads beyond its arguments.
- No `qd_data` edit.

It is Python because it stores Python objects (`DataRow`) for a Python consumer. That is the
language policy's orchestration case; there is no hot loop in it.

**How each condition is met.** The tests are in two files:
- `python/tests/test_split_cache.py`: 45 tests. They also pass in main's `.venv`, where torch
  is not importable [V, `AUDIT/v6-startup-2026-10-04/cache-tests-notorch.log`].
- `python/tests/test_split_cache_main.py`: 3 tests on the toy corpus.

1. **Opt-in.**
   - `--split-cache DIR` is off by default. Its help says "Off by default. Not recipe".
   - The state is the metric `split_cache` on every row of the run, attached in `_recorder`
     from a run-scoped dict that `main` clears when it starts. It is a `Ran` whose value is
     `hit`, `miss` or `corrupt`, whose detail starts `key <sha256>; ` and gives the reason.
     It is a `NotRun` when the key could not be computed; the run then rebuilds uncached.
   - `passed` is True when the cache served rows that passed every check, or stored the
     rebuild's. It is False on `corrupt`, and when rebuilt rows could not be stored.
   - With the flag off, nothing is attached: a row is byte-for-byte what it was, as
     `native_spancheck` is absent when its flag is off. Item 1's toy parity test still passes
     unchanged.
   - A hit logs `split cache: READ FROM the split cache <dir>/<key>.rows.pkl -- N train + M
     val rows, NOT rebuilt by this run`.
2. **Pickle is code execution on load.**
   - Before anything is read, the directory, the sidecar and the entry are each refused if:
     - another user owns them;
     - they are group- or world-writable;
     - they are symlinks;
     - they are not a directory or a regular file, as the case requires.
   - The checks are made on descriptors, not names: the directory is opened
     `O_DIRECTORY|O_NOFOLLOW` and fstat'd, and each file is opened `O_NOFOLLOW` relative to
     that descriptor and fstat'd. The file that was checked is the file that is read.
   - A bad directory refuses the run at argv time, before the shard set is opened. A bad
     entry is `corrupt` and is replaced by a fresh rename, which replaces a planted symlink
     itself and writes nothing through it (tested).
   - A second guard: the unpickler resolves only classes from `qd_data.`/`qd_train.` plus six
     builtin classes. No function resolves, so REDUCE cannot reach `os.system`. Tested: a
     planted `os.system` pickle whose sidecar sha256 was forged to match is refused, and its
     command never runs.
   - **The sha256 sidecar is an integrity check, not a security boundary.** Whoever can write
     the entry can write its sidecar. It catches truncation, bit rot and a writer that
     stopped part-way. Against another local user, the protection is the ownership, mode and
     symlink checks, and behind them the restricted unpickler.
3. **Atomic writes.**
   - Each file is written to a fresh `O_CREAT|O_EXCL|O_NOFOLLOW` 0600 temp file in the cache
     directory, fsynced, renamed over its name, and then the directory is fsynced. The entry
     goes first and its sidecar second. The entry is pickled as a stream through a hashing
     writer, with no 1.7 GB bytes object.
   - A reader that finds an entry without its sidecar treats it as a miss. A sidecar without
     its entry is a miss too.
   - **The race.** Both lanes miss at the same moment and write the same key. That is safe
     because the pickle is deterministic: the probe above produced the same bytes in two
     processes with different hash seeds, so the two renames put identical bytes in place.
     - Tested with real processes, three rounds: two `spawn` writers released by one barrier,
       and a reader loading 40 times meanwhile. Every read was a miss or a hit with equal
       rows, and the directory ended with exactly one pair and no temp file.
     - If the pickle ever stopped being deterministic, a reader could hold one writer's
       sidecar beside the other's entry. That is a sha256 mismatch, so `corrupt`, never the
       other writer's rows. Tested by placing such a pair deliberately.
   - The only deletion other than eviction: a writer whose own write fails removes its own
     temp file. Tested: a failed write leaves the directory as it was and the metric says
     "not stored".
4. **A corrupt entry is loud.**
   - Five corruptions are tested: a flipped byte, a truncation, an unparseable sidecar, a
     sidecar naming another key, and a sidecar without its rule-3 record. Each gives:
     - a `split cache: CORRUPT entry <key>: <reason>` line;
     - a rebuild, and a fresh entry the next run reads as a hit;
     - a metric that says `corrupt` with the reason and `passed` False, never `hit`.
   - Rows that unpickle but disagree with the build are `corrupt` too: a val row whose content
     hash is not `val.json`'s, or a row count that is not the manifest's `n_rows`. The rebuilt
     rows must pass the same checks before they are stored; when they fail, nothing is
     written and the metric says "not stored".
   - The checks are against `<out>/data/pool/{train,val}.json`: both `n_rows`, and every val
     row's id and content hash. The shard header's `n_sequences` (558,790) is not checked: it
     is not 1:1 with the 487,407 train rows.
5. **Bounded.**
   - At most 2 keys per directory, `MAX_ENTRIES`. After a successful write, the oldest keys
     by mtime are evicted, never the one just written, and each eviction is logged
     `split cache: EVICTED entry <key> (mtime, bytes)`.
   - Unknown files are not touched. Temp files left by a killed writer are counted, named in
     the log and left in place; deleting them is a human decision (below).
   - Other bounds:
     - an entry is at most 16 GiB and a sidecar at most 16 MiB;
     - a keyed tree is at most 200,000 files;
     - one key hashes at most 64 GiB.
6. **Rule 3.** `DataRow` has no file-path field (`row_id`, `source_id`, `host`, `family_id`,
   `repo_key`, `identity_key`, …), so the rule is checked on two sides.
   - Every row's `family_id` is checked against `DataConfig.held_out_families`.
   - `qd_train.data_access.assert_path_not_held_out` runs over every file the key covers: the
     same check `qd_data.defect_class` runs on its own reads.
   - Both run before a store, and the sidecar records them (families, rows checked, paths
     checked). Both run again on every load, and a violation raises `HeldOutViolation`; it
     is not rebuilt around. Four tests: a rebuilt row from a held-out family, a forged cached

### The A/B, pre-registered before any timed run

Written and committed before the first timed run. The commit is named under Commits.
- **Arms.**
  - OFF: no flag.
  - HIT: `--split-cache build/v6-profile/split-cache-ab`, with a warm entry.
  - One MISS run first, on an empty directory. It writes the entry and prices the store.
- **Order.** MISS, then OFF, HIT, OFF, HIT, OFF, HIT: interleaved, N = 3 per arm. All seven
  run in one `tools/mac_heavy.sh` job.
- **Window.** The v5 Mac argv of `build/v6-profile/run_profile.sh`. Each run builds the split,
  the val set and the OOD suite, then stops at `_ft_row`, before any model load: the window
  item 2 timed.
- **Measures.** Wall seconds and peak RSS from `/usr/bin/time -l` around the Python process.
  Each arm's statistic is its min of 3.
- **GO needs all four:**
  1. min(OFF) − min(HIT) ≥ **60 s**. The expected saving is ~185 s [I]: a ~202 s rebuild
     against ~1 s key, ~10 s load and ~1 s checks.
  2. HIT's peak RSS ≤ OFF's peak RSS.
  3. MISS wall ≤ min(OFF) + 30 s, and MISS peak RSS ≤ OFF peak + 2 GiB: the store must not
     double memory.
  4. In every HIT run, the downstream window is identical to every OFF run's. The window is
     the lines from `val set:` to the run's stop: the val set, the permutation second pass,
     the needle suite, the OOD suite, the shard-set facts, and the stop's traceback. Before
     comparing:
     - timestamps, `split cache:` lines and the time report are removed;
     - every `<n> s` duration is replaced by `<t> s`, because the OOD suite's own
       `minhash:`/`lsh:` lines print seconds.
  - `AUDIT/v6-startup-2026-10-04/ab_compare.py` computes all four bars from the logs.
- **Otherwise NO-GO.** The negative result is recorded here, the flag stays off by default
  (it already is), and the recommendation is not to merge it.
- **If mac_heavy's 32 GiB RSS cap trips,** the A/B stops and that is reported. It is not
  worked around.
