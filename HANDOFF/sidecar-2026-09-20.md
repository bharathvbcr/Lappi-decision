# SIDECAR lane — 2026-09-20

**A checkpoint was a JSON document, and at the real model's size that was the wrong shape.**
`TrainStep.state()` was documented *"JSON-serialisable state for a checkpoint"* and
`Checkpoint` enforced it literally: a tensor had to become a list of Python floats to be
stored at all. Today the weights go to a safetensors sidecar beside the JSON, the JSON keeps
the bookkeeping and every tensor's digest, and **the protocol itself changed** — this was a
contract change, not only an implementation change.

Nothing was committed. No GPU was rented, launched or touched.

---

## 1. The headline number, and a correction to the brief that opened this lane

The lane brief stated **23x**: 65.2 GB of JSON against 2.80 GB of bf16 safetensors for the
1,401,501,504-parameter remapped model. **That comparison is not content-constant, and the
real factor is 5.7.**

* the 46.5 bytes/parameter behind "65.2 GB" is a *whole rung-0 checkpoint* — weights **plus
  AdamW's two moments**, about three stored numbers per model parameter;
* the 2 bytes/parameter behind "2.80 GB" is **bf16 weights only**, one number per parameter.

Measured today on the real `Rung0Step`, the same content encoded both ways, moments present:

| | JSON | JSON + sidecar | ratio |
| --- | --- | --- | --- |
| rung 0, width 64 (172,224 params, 145 tensors) | 11,856,462 B = **68.84 B/param** | 2,127,190 B = **12.35 B/param** | **5.57x** |
| rung 0, width 128 (639,360 params, 145 tensors) | 44,025,438 B = **68.86 B/param** | 7,733,214 B = **12.10 B/param** | **5.69x** |

Per stored number: **22.89 bytes of decimal text against 4.02 raw.** Scaled to
1,401,501,504 trainable parameters with fp32 moments, about **97 GB per checkpoint against
about 17 GB**.

**Two things follow, and the second is the one that matters.**

1. The saving is real and large — 80 GB per checkpoint — but it is 5.7x, not 23x, and any
   plan built on 2.80 GB per checkpoint is under-budgeted by 6x.
2. **2.80 GB is not a checkpoint.** It is weights with no optimizer state. A resume from it
   restarts Adam's moments at zero and does not reproduce the trajectory, which is the
   property S5 rests on. The number to plan the GH200's disk against is ~17 GB per
   checkpoint, not 2.80 GB.

**Why JSON's cost is not a constant, which is also why my first attempt at this measurement
was wrong.** `tolist()` widens a float32 to a float64 whose shortest round-tripping decimal
is 17 significant figures, so a trained weight renders as `-0.8201345205307007` (20 bytes)
while `0.5` renders as `0.5` (3 bytes). A test I wrote with values like `float(i % 97) + 0.5`
measured 5.9 B/param and would have passed no matter what the sidecar cost. It now walks the
float32 bit space so every value needs its full mantissa. The sidecar's cost does not depend
on the values at all; that is a second, smaller reason to prefer it.

## 2. The design decisions the lane brief asked me to answer

### Two files, and the JSON is the commit record

A single container was considered and rejected on one hard constraint: `run_control.py` is
imported by the torch-free suite, which has neither torch nor safetensors. A format that
always needs safetensors turns that whole gate red. So **a checkpoint with no `TensorRef`
writes exactly one JSON file, byte-for-byte as before** (pinned by
`test_a_checkpoint_with_no_tensors_still_writes_exactly_one_file`), and the sidecar exists
only when there are tensors. `safetensors` is imported lazily inside the write path;
`safetensors==0.8.0` is already in `stack/train.lock` and in the ml venv, so **no dependency
was added**.

The pair is atomic together by three mechanisms, none of which is the filesystem:

* **the sidecar is written first and the JSON last.** Until the JSON lands, nothing names
  the sidecar and it is unreferenced debris. The JSON is the commit, exactly as the
  directory fsync is for one file.
* **the sidecar's filename contains the tensor set's digest** — `<stem>.<digest16>.safetensors`.
* **the JSON records every per-tensor digest and one set digest, and `payload_digest`
  covers the JSON.**

### What identifies a matched pair: the digest, and deliberately not a uuid

A uuid would distinguish two checkpoints whose tensors are byte-identical — the one case
where sharing the bytes is both correct and free — and would say nothing about whether a
file's *contents* are the ones the metadata was written from, which is the only question
that matters. The digest answers that; a uuid answers a question nobody asked.

**Both decisions were graded against the design that was not chosen, on the same data.** A
fixed sidecar name, interrupted exactly where it matters — tensors landed, metadata did not:

```
  before:  ckpt.json -> ckpt.safetensors = b'OLD-WEIGHTS-step-4'
  ...killed after the tensors landed and before the metadata did.
  after :  ckpt.json still says step = 4
           ckpt.safetensors now holds = b'NEW-WEIGHTS-step-8'
```

Nothing about that pair is wrong on its face: the file named is present and parses. It
resumes, reports step 4, and trains from weights that are not step 4's. The shipped design,
same interruption, same data:

```
  old sidecar ckpt.1642fa76f6c5810c.safetensors  present=True
  new sidecar ckpt.4a1363152458557d.safetensors  present=True
  metadata unchanged: True
  the checkpoint still reads, and its weights are the OLD ones: True
```

And a manifest carrying dtype/shape/nbytes but no digest accepts a swapped sidecar — the
impostor matched all three fields; the shipped code refuses on the digest.

### `MAX_CHECKPOINT_BYTES`: the number did not move, what it bounds did — stated, not nudged

`MAX_CHECKPOINT_BYTES` is **1 GiB, byte-for-byte unchanged**. It used to bound a body
carrying the weights as decimal text; it now bounds the position, the schedule, the loss log
and the per-tensor digests, and nothing whose size scales with the model. That is a
**tighter** bound on what it measures — everything it used to permit it still permits — so
no gate was widened (rule 2).

`MAX_SIDECAR_BYTES = 32 GiB` is a **new bound on a new payload**, not a relaxation: before
this lane a model state of that size could not be written at all, so there is no older,
tighter bound that was loosened. Its number is derived rather than guessed:
`QWEN3_5_2B_TEXT.trainable_params()` = 1,881,825,088 and `ADAMW_FP32` keeps two fp32 moments,
so the widest checkpoint this repository can construct is 1,881,825,088 × 12 =
**22,581,901,056 bytes (21.03 GiB)**. 32 GiB is 1.52x that.
`test_the_sidecar_bound_is_derived_from_the_model_it_has_to_hold` pins the arithmetic
against `qd_train.memory` so the two cannot drift apart in silence, and asserts the headroom
is under 2x so the bound still bounds. `MAX_SIDECAR_TENSORS = 1 << 20` bounds the fan-out.

### bf16 round-trip: exactly round-tripping, measured

**Exact, by construction and by measurement.** The bytes never pass through a float in
either direction — `t.detach().to('cpu').contiguous().flatten().view(torch.uint8)` out,
`torch.frombuffer` back.

* All **65,280 finite bf16 bit patterns** written to a real file and read back:
  byte-identical (`test_the_sidecar_is_exact_for_every_bfloat16_bit_pattern`).
* The eleven bf16 corner cases — ±0, both smallest subnormals, both largest finite, ±inf,
  NaN with payload 0x41, 1.0 — through `write`/`read`: all eleven bit-identical.
* The same eleven through the **old** `tolist()` path: the nine finite ones are bit-identical
  (bf16→float64→bf16 is exact for finite values), `±inf` and `NaN` cannot be written as JSON
  at all, and the NaN payload would silently normalise 0x7FC1 → 0x7FC0 if they could be.

So the old path was not *lossy* for finite weights — it was 5.7x the size and could not
represent the non-finite patterns. Device discipline is unchanged and still three-valued:
**cpu measured bit-exact, mps measured NOT bit-exact, cuda NOT RUN.**

## 3. The refusal that would have been retired in silence

`_refuse_unwritable` refused a non-finite float for two reasons: JSON writes it as a bare
`NaN`/`Infinity` token that is not JSON, **and** a non-finite parameter is a run that has
already diverged. Only the first stops applying in a sidecar, where the bit pattern
round-trips perfectly. Moving the weights out would have dropped the second without saying
so. Measured, with the scan disabled:

```
  With the scan removed (probe disabled), the diverged run is checkpointed happily:
    written and read back, NaN intact: True
    -> a refusal retired in silence by a format change.
```

So it is reimplemented against the bytes. `_first_non_finite` slices out the byte holding
the exponent's high bits and runs one `bytes.translate` over it at C speed, chunked at 4Mi
elements so probing a 2.80 GB payload does not allocate 2.80 GB more. **Exact, not sampled**,
and checked against `torch.isfinite` as an independent oracle:

| | checked | mismatches |
| --- | --- | --- |
| float16 | **all 65,536 bit patterns**, each alone and in bulk (2,048 non-finite) | 0 |
| bfloat16 | **all 65,536 bit patterns**, each alone and in bulk (256 non-finite) | 0 |
| float32 | 1,000,000 elements over 200 buffers, biased toward the all-ones exponent | 0 |
| float64 | 1,000,000 elements over 200 buffers, same bias | 0 |
| chunk boundaries | indices 4194303 / 4194304 / 4194305 / 8388607 for bf16 and f32 | 0 |

The exhaustive half is repeated inside the suite
(`test_the_non_finite_scan_is_exact_over_every_sixteen_bit_pattern`) with a second,
independent oracle — a mask over the whole 16-bit value — so it runs in both gates.

## 5. What it costs per checkpoint boundary

Measured on this host, 512 MiB bf16 payload:

| | time | rate |
| --- | --- | --- |
| non-finite scan | 0.163 s | 3.30 GB/s |
| `TensorRef` build (copy + validate + scan) | 0.151 s | — |
| sha256 digest | 0.176 s | 3.05 GB/s |

The set digest hashes the per-tensor digests, not the bytes again — but `TensorRef.digest()`
was being recomputed by both the manifest and the set digest, **three full passes over the
payload per checkpoint**. Now cached: second call 0.0000 s, set digest free. For a 2.80 GB
payload that is ~0.9 s of every checkpoint boundary removed. Equality is unaffected by the
cache (`compare=False`), asserted directly.

## 6. Evidence: why there is no grafted pre-fix test, and what replaces it

`TensorRef` did not exist before this lane, so a test grafted onto the pre-fix code dies on
`ImportError` — a kill by the wrong mechanism, which proves nothing. Per the lane brief, both
behaviours were measured instead and are quoted above: §1 (the size, both ways on the same
content, on the real step), §2 (the fixed-name design losing a checkpoint, and the
digest-free manifest accepting a swap), §3 (the divergence refusal disappearing when the
scan is removed).

One more thing worth saying about the pre-fix baseline: **`git show HEAD` is not it.** HEAD
is `8b9df39`, which predates the RESUME lane entirely — its `_portable`/`tolist()` codec is
uncommitted working-tree state. The pre-fix encoding was therefore *reconstructed* exactly
(pre-fix `_portable` returned `{"__tensor__": {"dtype", "shape", "data": flat.tolist()}}`)
and applied to the same tensors, which is what the table in §1 compares. That is stated
because a shadow package loaded from HEAD would have silently measured the wrong baseline.

## 9. Open

* `GAP-SIDECAR-RETENTION-ACROSS-SLOTS-IS-THE-DRIVERS-JOB` — **the most important one.**
  `write` retires the previous sidecar at the *same path*, so one slot holds one sidecar. It
  deletes nothing across slots, so `step-4/8/12.json` leaves three ~17 GB pairs. The disk
  problem is 5.7x smaller and still unbounded in the number of checkpoints. Whoever wires
  `on_checkpoint` must choose one slot or implement keep-N, and say which.
* `GAP-SIDECAR-BACKBONE-HAS-A-SECOND-SIDECAR-CONVENTION` — `QwenDecisionStep.state()` had
  hand-rolled its own safetensors file plus an absolute `weights_path`, *because* the
  contract said JSON-only. During this lane the BACKBONE lane converged it onto `TensorRef`.
  That is the right outcome and it was concurrent, not coordinated. This lane did not edit
  `backbone.py` or `test_backbone.py`; their owner should confirm no private sidecar
  remains and fix the docstrings that still call `TrainStep.state()` "JSON-serialisable".
* `GAP-SIDECAR-BIG-ENDIAN-AND-CUDA-ARE-NOT-RUN` — §7.
* `GAP-SIDECAR-DEVMAP-CHECKPOINT-BLAST-RADIUS-IS-A-LOWER-BOUND` — `devmap_explore` on
  `Checkpoint` carried `walk_incomplete` (depth 3; 14,693 of 32,081 unresolved attribution
  sites; 20 of 39 definitions shown). What actually closed it was running both suites in
  full, which is evidence from execution, not from the index.
* `GAP-SIDECAR-GITPULSE-BLIND-TO-LANES-IN-ONE-WORKTREE` (revised) — the first version of
  this record said `gitpulse_insights` reported no overlap. **It does not.** Run, it reports
  `overlapping_files=3` — `gaps.jsonl`, `python/qd_train/ledger.py`,
  `python/tests/test_ledger.py` — contended with a second worktree,
  `.claude/worktrees/devmap-dead-code-hardening-fc226b`. That facet works. The blindness is
  that every facet counts *worktrees*, so three lanes inside this one are one row
  (`worktrees.count=2`, `agents.sessions=1`). **Merging that branch will conflict on
  `gaps.jsonl`; it is append-only, so the resolution is the union of both sides' lines.**
* **Still nothing writes a checkpoint.** The RESUME lane's open item is unchanged: the
  machinery is correct, `train_rung0` has no `resume_from`, and no driver passes
  `on_checkpoint`. This lane made the format usable at the real model's size; it did not
