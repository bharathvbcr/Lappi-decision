## What converged, and where the single owner lives

**`qd_train.artifacts.line_start_indices`** now owns "where does a line begin", beside
`bucket_for` and for the reason that module's docstring already gave for `bucket_for`.

The recorded gap said there was one Python implementation (`shards.line_starts`) against
the Rust. There were **two**, and the record missed the second:

| implementation | unit | reached by |
| --- | --- | --- |
| `crates/qd-runtime/src/context.rs:156` `Context::line_starts` | bytes | the runtime — canonical for the whole system |
| `python/qd_train/shards.py:180` `line_starts` | characters | S4's writer |
| `python/qd_train/byte_context.py:88` `line_starts` | bytes | rung 0, via `qd_train.mutate_adapter` |

Same name, same package, same question — the shape that has bitten this repo five times.
And they were **not** equivalent:

```
shards.line_starts("")        == [0]     # one line
byte_context.line_starts(b"") == ()      # no lines
```

Both suites were green because each was pinned to the five vectors of
`answering_procedure.rs::the_pointer_head_ranges_over_the_contexts_line_starts_plus_the_abstain_row`,
and **not one of them is the empty string**.

`Context::line_count` (`context.rs:167`) is `0` for an empty context, asserted by
`context.rs::an_empty_context_is_a_legal_value_not_an_error`, and `answer.rs:70` sizes the
pointer head at `line_count + RESERVED_NOUL_ROWS`. So an empty context serves the abstain
row alone, the byte path was right, and S4 was wrong.

- `shards.line_starts` is now a two-line delegation to the canonical owner.
- `byte_context.line_starts` **cannot** be merged — its offsets *are* its model's
  positions, while S4 needs character offsets for a tokenizer's offset mapping. It is
  pinned instead, vector for vector including the empty input, by
  `test_artifacts.py::test_the_byte_path_line_rule_is_this_one` and
  `test_shards.py::test_the_two_python_line_rules_agree_vector_for_vector`.
- A **third** statement exists and could not be converged: `qd_data.mixture._line_span`
  (`mixture.py:121`), the gold's line *number*, in another lane's module. Pinned by
  `test_shards.py::test_the_gold_producers_line_numbers_index_this_line_grid`, with a
  negative control that a whole-line shift must fail every vector.

## What is ready to run the day a tokenizer exists

`write_shards(..., decode=tokenizer.decode)` → `shards._assert_spans_decode_to_their_text`.
Three statements, each against **decoded text**, none consulting the candidate set:

1. each checked token decodes to exactly the characters its offsets claim;
2. the ids round-trip to the text the spans were measured against
   (HuggingFace's `clean_up_tokenization_spaces` operates over a *sequence*, so (2) does not
   follow from (1));
3. every character offset recorded as a line start is a line start of the **decoded** text
   under `line_start_indices` — the statement `GAP-SPAN-HEAD-LINE-MAPPING-BPE-UNVERIFIED`
   asks for.

Proven to bite today against three dishonest stand-in decoders. **Never run against a real
BPE.** In the repo venv it runs only against a byte-level stand-in, where a line start *is*
a byte offset and none of the three can fail for the reason they exist.

The other leg needs no tokenizer and is covered: gold line number → character offset is
character-space arithmetic, checked against an independent baseline (the rendered region's
own line split) over all 19 pointing rows, mutation-proven by M5.
