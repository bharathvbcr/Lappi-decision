# LEDGER lane — 2026-09-19

`ledger/` was empty. Not sparse: zero rows, ever, against a 27KB module with a hash chain, a
six-condition promotion verdict and a `run_kind: "build"` added one lane earlier specifically so a
build-and-test lane could comply with repo rule 5. Four lanes had noticed, printed command output
instead, and said so honestly in their handoffs. Four out of four is not forgetfulness.

This lane built the missing path, used it, and found two real defects doing so — one in the ledger
that predates this session, one in the recorder written today, caught by the first real row rather
than by reasoning about the code.

---

## 1. The reading of rule 5 this lane implemented

Rule 5 has two clauses with different scopes:

> **Nothing is green that was not run.** GPU suites that cannot run in the agent's environment are
> reported as **not run**. *A number in a report cites a ledger row or is not in the report.*

The first clause governs **runs**. The second governs **numbers in reports** — and that is the one a
build lane trips. It is implemented literally:

> **A lane iterates as freely as it likes while working, and records the one run whose numbers it is
> about to publish.** Every `pytest` during development gets no row. The count pasted into a
> `HANDOFF/`, a doc or a gap record does.

**This is the wider of the two available readings** and the choice is deliberate, not automatic. The
narrow reading — rule 5 governs training numbers; a test count is "command output" and is exempt —
is genuinely defensible: a test count is cheaply reproducible by anyone, which an accuracy number is
not, and ceremony nobody keeps up is worse than no ceremony. I did not take it, for three reasons
that are specific to this repo rather than general:

1. **The counts are the load-bearing numbers here.** There is no model yet. "Is the repo green" is
   the only decision the ledger is currently being asked about, and it is answered entirely in test
   counts.
2. **They have already been wrong, this session, in ways a row catches.** Five vacuous tests; three
   false survivors traced to `.pyc` caching; and the brief's own baseline — "1094 passed, measured
   at 22:10" — measured **1104** when this lane ran it at 22:20. The cause turned out to be another
   lane adding tests (+17 test functions in `test_run_control.py`, net +10 collected, mtimes
   22:17–22:22). That took mtime forensics and a `git diff` to establish. A row pins commit, dirty
   state, host, wall clock and exact argv, and would have answered it in one lookup. That is the
   entire argument for rows in one concrete incident.
3. **Narrowing the rule was the alternative I was invited to argue for, and it fixes nothing.** The
   four lanes did not skip the row because they disagreed with rule 5. They skipped it because there
   was no way to obey it that cost less than not obeying it. Narrowing the rule would have ratified
   that, and the next lane with a number that *does* need a row would have hit the same wall.

What I did **not** widen: nothing about the rule was weakened, no gate moved, no threshold changed,
no run reclassified. `quick` still excludes; `build` still never promotes.

## 2. What a lane must now do to comply — one command

```
PYTHONPATH=python .venv/bin/python -m qd_train.ledger record \
  --toolchain "cargo 1.98.0 / CPython 3.13.14 (.venv)" \
  --suite cargo_test_workspace="cargo test --workspace" \
  --suite pytest_python_tests=".venv/bin/python -m pytest python/tests -o addopts="
```

It runs each suite, parses the counts, writes one `run_kind: "build"` row, and prints **the row id
alone on stdout** — everything else goes to stderr, so `ROW=$(… record …)` works. Cite that id.

Also: `verify` (recompute the chain; `docs/ledger-schema.md` had claimed a `qd-ledger verify`
binary since S6 and no such binary ever existed), `show --row-id`, `verdict --row-id`.

Design notes that matter for whether the next lane keeps using it:

- **Four outcomes per suite, kept distinct.** Binary missing → `not_run` naming the binary, never a
  zero. Timed out → `not_run`. Counts parsed → `ran`, where `passed` requires **exit 0 AND zero
  failures** (a harness can exit non-zero with a clean summary). No counts → exit ≠ 0 gives
  `ran/failed` (a compile error is a real failure, and calling it "not run" would let a broken build
  sit in the record as "nothing was measured here"); exit 0 gives **`not_run`**, because a pass with
  no counts cannot be told from a suite that collected nothing.
- **Three exit codes**, because `$?` is a trace like any other: `0` all passed, `1` something ran and
  failed, `3` nothing failed but something did not run.
- **Pipelines are refused, not split.** `cargo test --workspace | tail -5` would hand `|` to cargo as
  a test-name filter and cargo would exit 0 having run nothing — a green row for a run that did not
  happen.

## 4. What broke when the machinery met real data

### 4.1 The recorder claimed complete coverage for a truncated run — found by row 1

Row 1 recorded `suite.cargo_test_workspace: FAILED value=299 coverage=301/301` against a 347-test
baseline. cargo had not lost 46 tests. **cargo is fail-fast**: after the first failing test binary it
stops and never builds the rest, and the tests in those binaries appear in no summary line at all —
not as `ignored`, not as `filtered out`. Summing what the harness printed therefore produced
`n == n_total` for a run that covered a fraction of the workspace.

That is this repo's forbidden shape — *a check that could not run reading the same as one that ran* —
reproduced inside the tool written to prevent it, and reasoning about the code did not catch it.
Only a real row did.

**Fixed.** `SuiteCounts` carries `collection_complete`, set by detecting each harness's own abort
announcement (`error: test failed, to rerun pass …`, `could not compile`, `build failed`;
`stopping after N failures`, `Interrupted:`). When it is false, `as_tristate` keeps `value` and
**drops the coverage pair**, because nobody measured the eligible population. `Ran` carries `n` and
`n_total` together or not at all, so this is exactly the encoding the tri-state already provides:
`coverage_str()` reads `coverage unstated` and `is_complete_coverage` is False. Row 3 shows it:
`coverage=coverage unstated`. pytest's `-x` has the identical hole and is covered too.

### 4.2 Two concurrent appends break the chain permanently — pre-existing, in `Ledger.append`

`append` read `last_line_hash()` and *then* opened the file. Between those two steps another process
can append; both writers then claim the same predecessor, and `verify_chain` refuses the file from
that line onward **for good**, on a log whose entire premise is that you do not go back and fix it.
The existing comment credited `O_APPEND` with preventing this. `O_APPEND` makes each `write` atomic
and says nothing about the read-then-write window.

Reproduced before fixing, 6 processes × 5 rows released from a common start time:

```
LedgerChainError: line 2 (row w2-0): prev_row_hash is None but the previous line
hashes to 'efbdd1ff55a353e92ffdceaec00de49a134cb289dbd0625d29b7c8d32386a39d'.
History was edited, reordered, or truncated.
```

**Fixed.** `append` holds an exclusive `fcntl.flock` on the ledger fd across read-predecessor →
duplicate-id check → write, bounded at 60s, refusing loudly rather than racing. `ledger/` was empty,
so no existing row was affected — but the *first* two lanes to record at once would have corrupted
the decision record on contact. Given how many sessions write this tree, that was days away at most.

### 4.3 The promotion machinery, on real rows

`verdict --row-id ee059995-…` returns **REFUSED with 23 itemized reasons across 2 rows**, and every
one of the six conditions fires: status ≠ completed (1), `build` never promotes (6), 1 distinct seed
(3), all five gates `not_run` (4), all four controls `not_run` (5). Condition 4 is the one that
matters and it behaved: `_fill_unreported` wrote explicit `not_run` tri-states for gates the build
run never evaluated, and each one *blocked* rather than dropping out of the conjunction. Nothing
came out silently true.

Two observations, neither a defect:

- Every build family reports `1 distinct seed(s) [0]`, since `Protocol.for_build` defaults `seed=0`.
  Accurate but redundant next to condition 6, which already forecloses the family.
- The verdict is O(rows × 9) lines. Verbose by design — "refusals are itemized" — but a training
  family of three rows will print ~27 lines. Left alone; itemizing is the point.

Also exercised on real data: the `row_id` collision check (every append scans existing ids;
`uuid.uuid4()` collided with nothing) and the `prev_row_hash` chain across three rows written by
three separate processes minutes apart.

### 4.4 Two documentation claims that were false against the code

Both in `docs/ledger-schema.md`, both fixed there; the code wins.

- `qd-ledger verify` — **no such binary ever existed**, in this repo or anywhere. `verify_chain`
  had four callers, all in `test_ledger.py`. The command in §2 is the real one.
- `row_id` documented as **ULID**. The code has always written `uuid.uuid4()`.

  blocks all future appends. Correct-but-slow and arguably fail-closed-by-accident; at 3 rows it is
  invisible. Worth an index or an id-only scan before the ledger has thousands of rows.

## 7. First command for the next lane

```
PYTHONPATH=python .venv/bin/python -m qd_train.ledger verify
```

Expect `chain verifies: N row(s)`, exit 0. If it reports a break, **stop** — the chain is
append-only and a break is not repairable by editing; find which two writers raced and say so.

Then record your own verification before you write a number into a handoff:

```
PYTHONPATH=python .venv/bin/python -m qd_train.ledger record \
  --toolchain "<what ran it>" --suite <name>="<command>"
```

`docs/ledger-schema.md` has the schema, the four suite outcomes, the three exit codes and the rule
for when a run must be re-recorded after prose is written.
