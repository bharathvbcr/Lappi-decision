# MEMORY lane — 2026-09-20

**The question this lane owns: will it fit, and what happens when it does not?** Before
today nothing in this repository could answer the first half and nothing refused on the
second. The binary literally named `qd-preflight` — *"the environment-independent gate that
runs before a paid block"* — read every GPU's memory size and threw it away, and the
planner that builds batches bounded their rows but never their positions. Both are fixed.
The arithmetic that decides the rental is new, is torch-free so it runs in the gate, and is
labelled **arithmetic** on every number it emits, because this host has no CUDA device.

**The headline, for the GH200 96 GB that is already rented.** Full fine-tuning of the
1,881,825,088-parameter text tower fits, with room, and the 34,522-token bucket fits at
**8 rows per batch** — but only with **per-layer gradient checkpointing**, which
**nothing in this repository turns on**. Without it, one row of that bucket needs
**108.15 GB** against a 96 GB card. That is the finding: the card is big enough, the code
is not yet written to use it, and the gap between those two sentences is where the money
goes.

## 2. The memory arithmetic, from first principles

### 2.1 Parameters — measured, from the checkpoint's own tensor shapes

Read out of the safetensors header without torch, the same way
`tools/verify_checkpoint_inventory.py` does, and re-checked by a test that fails if the
constant in `qd_train/memory.py` ever drifts from the file
(`test_the_model_spec_matches_the_local_checkpoints_own_tensor_shapes`).

| component | parameters | share |
| --- | --- | --- |
| **text model (trained)** | **1,881,825,088** | 100% |
| tied embedding, 248,320 x 2048 | 508,559,360 | 27.0% |
| 18 x `linear_attention` layer @ 58,814,624 | 1,058,663,232 | 56.3% |
| 6 x `full_attention` layer @ 52,433,408 | 314,600,448 | 16.7% |
| final norm | 2,048 | — |

Sums exactly. The vision tower (331,416,576) and the MTP block (60,828,160) are dropped on
load and never trained, so neither is in the budget.

**One architectural detail that an assumed architecture gets wrong by a factor of two.**
`config.json` has `attn_output_gate: true`, and the shapes confirm what it means:
`q_proj` is `[4096, 2048]` where `num_attention_heads x head_dim` is `8 x 256 = 2048`. The
projection emits a **gate beside the query**, so the query activation is twice what the
head count suggests. `k_proj`/`v_proj` are `[512, 2048]` = 2 KV heads x 256, confirming GQA
4:1. A test pins the difference at exactly one `q_heads x head_dim` tensor per token.

Also read rather than assumed: `mamba_ssm_dtype: "float32"`, so the linear-attention
recurrent state is **fp32**, not the compute dtype. It is small — 16 x 128 x 128 x 4 = 1 MiB
per sequence per layer — but assuming bf16 would have halved it silently.

### 2.2 The optimizer — read, not assumed

Every optimizer this repository constructs is `torch.optim.AdamW`:
`qd_train/byte_train.py:206`, `tools/ft_toy_run.py:271`, `tools/real_ft_run.py:574`,
`tools/rung0_toy_run.py:393`. None passes `foreach`, `fused` or `capturable`, so the state
is two plain tensors per parameter — `exp_avg` and `exp_avg_sq` — in the parameter's dtype.

**And there is no mixed precision anywhere.** `rg -uu` for
`autocast|GradScaler|bfloat16|float16` finds nothing in `python/qd_train/` or `tools/`. So
the recipe the code *as written* implements is **pure fp32**: 4 + 4 + 8 = 16 bytes per
parameter. The checkpoint ships bf16. The gap between those is a recipe nobody has written.

### 2.3 Static state — two independent choices, four cells, none of them settled

**Two things move this number and they must not be reported as one.** The vocabulary
(whether the remap is applied) and the optimizer layout (whether an fp32 master copy is
kept). Carrying only the diagonal — the largest cell against the smallest — attributes an
optimizer decision to the vocabulary, which is what the first draft of this handoff did.

bf16 weights and gradients throughout; the difference is the master copy:

| | **with fp32 master** (2+2+4+4+4 = 16 B/param) | **no fp32 master** (2+2+4+4 = 12 B/param) |
| --- | --- | --- |
| **full vocab 248,320** (1,881,825,088 params) | 30.11 GB / **28.04 GiB** | 22.58 GB / 21.03 GiB |
| **remap vocab 13,787** (1,401,501,504 params) | 22.42 GB / 20.88 GiB | 16.82 GB / **15.66 GiB** |

```
  vocabulary slice   : 28.04 -> 20.88 GiB  =  7.16 GiB
  drop fp32 master   : 20.88 -> 15.66 GiB  =  5.22 GiB
  ------------------------------------------------------
  total              : 28.04 -> 15.66 GiB  = 12.38 GiB
```

**Neither choice has been made.** The vocabulary one waits on
`GAP-S2-NO-REAL-CHECKPOINT-PARITY` (section 2.4). The optimizer one waits on someone
writing the real-model `TrainStep` at all — and note that the recipe the code *as written*
implements is a third thing again, pure fp32 at 16 B/param, which lands on the same static
state as the fp32-master row (30.11 GB full vocab, 22.42 GB remapped) by a different route.

**The module expresses all four cells and hardcodes none of them**, because a budget tool
that can only state one layout is the same trap one level down. `OptimizerSpec` carries
`states_per_param`, `state_bytes` and `keeps_fp32_master` as three orthogonal fields, and
`param_dtype` / `grad_dtype` / `activation_dtype` are independent parameters;
`test_an_fp32_master_copy_costs_four_more_bytes_per_parameter` asserts the 4-byte
decomposition directly. `tools/memory_budget.py` prints three recipes side by side for the
same reason.

### 2.4 The remap is a quarter of the model, and it is already in the shards

The shard set's header says `vocab_size: 13,787`. The ids the trainer consumes are already
remapped; the embedding is **tied**, so slicing it to match lands once:

```
1,881,825,088  text model as shipped
  - 508,559,360  tied embedding at 248,320 x 2048
  +  28,235,776  tied embedding at  13,787 x 2048
= 1,401,501,504  trainable          (480,323,584 fewer — 25.5% of the model)
```

At 12 B/param that is **5.76 GB** of static state removed (5.37 GiB); at 16 B/param,
**7.69 GB** (7.16 GiB) — the 7.16 GiB in section 2.3's decomposition. It
also shrinks the fused-CE fixed cost by 8x, because `grad_weight` accumulates in fp32 at
the size of the projection weight: 2.03 GB at full vocab, 0.11 GB remapped.

**The caveat, carried because it is load-bearing.** Whether `apply_remap_to_model` performs
that surgery on the real `Qwen3_5ForCausalLM` is
`GAP-S2-NO-REAL-CHECKPOINT-PARITY`, which records that it is verified **against stub models
only**. So: budget the full-vocabulary column, treat the remapped column as upside, and
close that gap before relying on it.
`GAP-MEMORY-REMAP-SAVING-RESTS-ON-SURGERY-VERIFIED-ONLY-AGAINST-STUBS`.

### 2.5 Activations — a stated model, enumerated so it can be checked

`ActivationModel` lists the saved-for-backward tensors **one line per tensor** rather than
hiding a coefficient. Per token, at the measured shapes:

| layer type | elements/token | what dominates |
| --- | --- | --- |
| `linear_attention` | 43,008 | 3 x MLP @ 6,144, plus `in_proj_qkv` and `conv1d` @ 6,144 each |
| `full_attention` | 33,792 | 3 x MLP @ 6,144, plus the gated `q_proj` @ 4,096 |

- **no checkpointing**: `18 x 43,008 + 6 x 33,792` = **977,088 elem/token** = 1.86 MiB/token at bf16
- **per-layer checkpointing**: `25 x 2,048` boundaries + one 43,008 recompute peak = **94,208 elem/token** = 184 KiB/token

**This is a lower bound.** A real framework also keeps an RMSNorm's reciprocal, SDPA's
per-row logsumexp, the conv's padded input, and kernel workspaces. `SAFETY_FRACTION = 0.35`
is the stated allowance for all of it, applied to the dynamic term only and carried as its
own field so the enumerated figure and the allowance are never quoted as one number.
`GAP-MEMORY-ACTIVATION-TERM-IS-ARITHMETIC-NEVER-MEASURED`.

### 2.6 The attention matrix, which is not a tuning knob

If the `[heads, L, L]` score matrix is materialised — no flash, no memory-efficient SDPA —
it is, in bf16, per full-attention layer:

| width | elements | bytes |
| --- | --- | --- |
| 2,947 | 69,478,472 | 0.14 GB |
| 8,192 | 536,870,912 | 1.07 GB |
| 14,759 | 1,742,624,648 | 3.49 GB |

## 4. What was hardened, and the pre-fix failure each fix was measured against

Both fixes were demonstrated in **scratchpad mirrors**, never in the live worktree. Where a
grafted test would have died on a missing symbol — a kill by the wrong mechanism, and not
evidence of anything — the mirror was given the **name** and HEAD's **behaviour**, so the
kill is the assertion. Same technique as commit `e089d27`.

### 4.1 The preflight read every device's memory and discarded it — FIXED

`qd-preflight`'s own docstring calls it *"the environment-independent gate that runs before
a paid block"*, and its table says it answers *"Is there a usable CUDA device?"* It does.
It also reads each device's `cuDeviceTotalMem_v2` into `DeviceInfo.total_mem_gib`
(`cuda.rs:61`, `:174`). **That field then appears exactly twice more in the entire
repository**: once formatted into a display string (`cuda.rs:217`) and once as a literal in
a test fixture (`main.rs:174`). It was never compared to anything. The binary had
`--min-devices` and **no memory flag at all** — it counted devices and never sized them.

Pre-fix, in a mirror whose `check_device_memory` always passes (which is what no memory
check *is*, observationally):

```
---- tests::a_card_too_small_for_the_job_is_refused_before_the_money_is_spent stdout ----
panicked at crates/qd-preflight/src/main.rs:185:9:
24.0 GiB cannot hold a job that needs 40.0 GiB, and a gate that says it can is the gate
this check exists to replace

---- tests::the_whole_gate_refuses_a_box_whose_cards_are_too_small stdout ----
panicked at crates/qd-preflight/src/main.rs:203:9:
device_count alone passes this box -- that is exactly why counting devices is not checking them

test result: FAILED. 22 passed; 2 failed
```

Both die on the **assertion**. Fixed by adding `--min-memory-gib` and a fourth gate check,
`device_memory`, with the discipline the rest of the crate already has:

- **the smallest card decides**, not the average and not the largest — a job lands on one
  device, so a box whose cards differ is a box where "it fits" depends on the scheduler;
- **an absent requirement is `not_run`, never `pass`** — so `--require-all` exits **2**
  ("you do not know the state"), not 0. Returning `pass` here would reintroduce exactly the
  fail-open shape this crate's own docstring warns about;
- a non-finite or non-positive requirement **fails** rather than being treated as zero;
- zero devices **fails** rather than passing vacuously — `all()` over an empty list is true
  and this must not be.

Seven new tests; the crate goes **22 -> 29** and the workspace **355 -> 362**. The existing
`check_device_count` behaviour is asserted unchanged inside the new aggregate test, so the
refusal is demonstrably the new check's and not a regression in the old one.
`GAP-MEMORY-PREFLIGHT-READ-THE-DEVICE-SIZE-AND-DISCARDED-IT`.

### 4.2 A batch's rows were bounded; its positions were not — FIXED

`MAX_ROWS_PER_BATCH = 4096` exists and its docstring names the exact failure it prevents:
*"a narrow bucket turns a generous `batch_tokens` into a batch of tens of thousands of
rows, and the first sign of it is an allocator failure some minutes into a run."* But a
batch costs **rows x width**, and the only ceiling on that product was `batch_tokens`,
which nothing bounded. `_plan` refused a budget *below* the widest bucket — saying out loud
that *"silently emitting an over-budget batch is how an out-of-memory failure gets blamed
on the model"* — and accepted anything above it.

Measured pre-fix against the real 321-sequence shard set:

```
batch_tokens=      1,000,000: ACCEPTED --   9 batches, widest batch   966,616 positions
batch_tokens=    100,000,000: ACCEPTED --   8 batches, widest batch 1,380,880 positions
batch_tokens= 10,000,000,000: ACCEPTED --   8 batches, widest batch 1,380,880 positions
```

1,380,880 positions is roughly **260 GB** of activations at 184 KiB/token. Nothing refused
it. Fixed by `MAX_POSITIONS_PER_BATCH = 1 << 20`, refused in `_plan` beside the existing
too-small refusal, so the planner now fails closed in **both** directions. Pre-fix failure
of the new test, against a mirror given the constant's name and HEAD's behaviour:

```
>       with pytest.raises(ValueError, match="exceeds MAX_POSITIONS_PER_BATCH"):
E       Failed: DID NOT RAISE ValueError
```

**It is a backstop, not a gate, and says so in its own docstring.** It turns a mis-typed
`batch_tokens` into a refusal; it is not a statement about what fits. The bound that
describes a real device is `qd_train.memory.max_positions_that_fit`, which
`tools/memory_budget.py` prints per bucket. The value is ~1.9x the largest batch that fits
the biggest card on the menu (96 GB, best recipe, checkpointed: about 547,000 positions),
so no recipe that fits any real GPU reaches it, and it is comfortably above this model's
`max_position_embeddings` of 262,144 so the two refusals can never contradict each other —
which a test asserts. `GAP-MEMORY-BATCH-POSITIONS-WERE-UNBOUNDED`.

**One existing test had to change, and it was strengthened rather than weakened.**
`test_rows_per_batch_are_bounded_as_well_as_tokens` used `batch_tokens = width * 1000`
(1,596,000) as an arbitrary stand-in for "generous", which the new ceiling forbids. Its
assertion — `max rows <= 2` under a monkeypatched cap — is **unchanged**; the budget is now
`MAX_POSITIONS_PER_BATCH`, i.e. *the most generous budget the planner will accept*, which
is a strictly stronger question. The docstring records the change and why.

### 4.3 The estimator itself — `python/qd_train/memory.py` (new)

The missing owner. Torch-free, so it runs in the repo venv and is counted by `make gates`
— which is the point: the failure it replaces happens on a rented GPU, so the check for it
must not need one. **No new dependency.** 30 tests.

It refuses rather than warns, and it refuses in the case that matters most:

```python
if device_bytes is None:
    raise MemoryRefused(
        f"{where}: no device memory budget was supplied, so whether this step fits was "
        f"never checked. Refusing rather than starting: an unchecked budget must not "
        f"read like a checked one."
    )
```

Every refusal carries the full component breakdown — not a single total, because a number
that cannot be attributed cannot be argued with — and `StepFootprint.provenance`, which
reads *"ARITHMETIC, not a measurement ... No CUDA device was available to check it
against"* and is asserted by a test so it cannot be dropped in transit.

`tools/memory_budget.py` is its caller, and re-measures the checkpoint from disk rather
than trusting the module's constant. Without `--require-fit` it prints, in place of a
verdict: *"no device was checked. Rule 5: this is NOT a pass, it is an unchecked budget."*

**Three things worth saying out loud.**

1. **The cheapest fix is one parameter.** `n_buckets=16` clears the gate at 13.29% with the
   existing quantile rule, **no length cap, and not one sequence dropped**. The diagnosis in
   the brief — that equal-count quantiles over a heavy tail let the top bucket span
   14,759 -> 34,522 — is right; what it costs is a *count*, not a rule change. Log-spacing
   is strictly worse at 8 buckets (28.39% vs 26.19%) and only catches up at 16+.
2. **A length cap buys its rate by deleting corpus, and the table says how much.** Cap
   8,192 looks excellent at 8.99% — while discarding **120 of 321 sequences**, 37% of the
   corpus, to pass a gate about padding. Any row quoting a cap's rate without its kept
   count is quoting half a measurement.
3. **A bigger card does not retire this.** 26.19% against 15% is a gate failure whether or
   not the waste fits in 96 GB. What the GH200 changes is that rebucketing is no longer
   forced by memory — it is still required by the gate.
