### The JSON the fsucc waiter sees

The four words and the exit codes are unchanged (0 for a word, 3 for `refused`, 2 for usage).

Every `successor` decision whose envelope resolves now carries these keys under `detail`:

- **`cannot_clear`:** a list of `{arm, target, max, min, bound}`, with `bound` given as
  `{name: "U"|"L", n, n_total, value}`. An empty list means room was decided and every target
  has room.
- **`room`:** one entry per target of both arms. Each gives `room: true|false`, or
  `room: null` with `not_decided`.
- **`refused_because`:** now a **list** of strings prefixed `(c)`, `(b)` or `(a)`, in the order
  they were met. Before, it was a single string, used only for both-win.

The top-level `refused` field is that list joined with `"; "`.

If F's envelope itself does not resolve, the JSON has no `detail`. The reason then ends with
"room not decided".

No script in the repo reads `refused_because` (`rg -uu`), so the shape change breaks no reader.

**Room is decided before the arm ledger is opened (inferred).** So once F's three seeds each
have all four rows (ft, eval, needle control, and letter control from `box_f_controls.sh`),
`successor` reports `detail.cannot_clear` even if the arm ledger or the arms' rows are missing. In that case it still refuses on (b). The code path is the one
`a_missing_arm_row_and_a_target_without_room_are_both_listed` tests. A missing arm ledger
*file* takes the same `judge_arms` error path, but no test runs that exact case.
