## What the script does

- **Fills in place.** Each of the 29 `amendments_pending` items gains one of three appendices:
  - `Filled <UTC date>: …` (each value cites its source path or sha256);
  - `Pending after launch (freeze <date>): <what fills it>`;
  - `Not filled: <reason>`.
- **Anchors on text prefixes.** Each item is found by a prefix of its own text. The prefix must
  match exactly one item, at its expected index. If there is any 30th item, or any prefix is
  missing, the script refuses. An item amended later (a suffix appended) still anchors; a test
  covers that.
- **Leaves everything else alone.** The only key it drops is `draft`. Every other top-level key
  is checked to be equal to the DRAFT's. All edits are textual, so the layout is the DRAFT's.
- **Item 24 runs first, and can refuse.** It takes code.defect_class's share of the build's
  `shards/train` real tokens, computed with `v4_token_accounting.py`'s method: `offsets.npy`
  lengths, categorised by `sequence_index.json` row id.
  - Before using the method, the script re-runs it on v4's shard set. The result must reproduce
    `v4_token_accounting.json` exactly.
  - The manifest's `family_id` join must give the same defect token count as the row-id method.
  - It refuses below `2 × 256,919,831 / (3 × 306,926,895)` = **55.8048%**. Two-thirds of the
    rounded 83.7% is 55.8000%. A share between the two refuses and says it is in that rounding
    band.
- **Cross-input checks refuse a mismatched input set.** The following must agree:
  - the train manifest's, build row's and train header's `data_snapshot_hash` (the build row is
    the one whose hash matches; zero or two matching rows refuse);
  - the scan's `exclusions_sha256`, the row's `recipe.exclusions_sha256` and the train header's.
    The scan directory gets replaced, so this check is what ties the freeze to the scan the
    build actually used;
  - the pool's examples sha256, from its file, its manifest, `POOL-RESULT-v4.md`, the scan's
    corpus and the build row;
  - A7. `a7.json` must say `passed`, and its v5 val and held-out hashes must be this build's.
- **Hard refusals:**
  - an own-prose or contrast row in `val.json`;
  - code.defect_class val choice slots ≠ 2,304;
  - an attestation that is not CLEAN at the version `python/qd_train/exclusions.py` accepts;
  - an input of an unknown shape (it prints the traceback).
- **Expectations that do not refuse.** A mismatch is written into the text and listed in the
  summary:
  - item 1's 1,216 / 72 / 62;
  - item 3's `over_max_seq_len_composed_train` target 0;
  - item 15's zero-checks;
  - a new family over 1,000 val rows.
- **Never read or copied:**
  - held-out entries (`heldout.json` is read only up to its `entries` key);
  - `*.request.bin` and `pairs.tsv`;
  - `a7.json`'s `first_missing` / `first_extra`;
  - the zero-checks' key and utterance lists.

  A regex guard in `validate()` refuses any fill text that names those lists.

## If the freeze refuses on something that changed after 21:00Z

- **A 30th pending item, or a reworded item prefix.** Refusing here is by design. To extend the
  script:
  1. Add the new item's prefix to `ANCHORS`, at its index.
  2. Give it a branch in `Freeze.fill()`: a fill, `.pending = …`, or `.not_filled.append(…)`.
     An item with no text refuses.
  3. Re-run `python3 AUDIT/finalize-2026-10-03/test_apply_v5_freeze.py`.
- **The reader patch.** It was checked against v5-build at about 21:00Z, and v5-build is still
  moving. Before committing, re-check it with
  `GIT_INDEX_FILE=<tmp index> git read-tree v5-build && GIT_INDEX_FILE=<tmp index> git apply --check --cached AUDIT/finalize-2026-10-03/v5-freeze-readers.patch`.
- **Two build rows with one `data_snapshot_hash`.** If the Mac build is re-run identically into
  the same ledger file, the script refuses until one row is left or the lead points
  `--build-ledger` at a file with the intended row only.
