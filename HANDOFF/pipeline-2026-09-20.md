# PIPELINE lane — 2026-09-20

**Subject.** Nobody had ever run the data -> shards path end to end with a real tokenizer.
Every test drives it with a byte-level stand-in, and that stand-in cannot fail the checks
that exist for BPE: in byte space no token straddles a line boundary, every `decode([id])`
is exact, and the trailing answer letter is always a token of its own. The coordinator ran
one piece of it against `Qwen/Qwen3.5-2B-Base` this morning and found the span head refusing
60.1% of real source files. This lane ran the rest.

**Result in one line.** The path runs end to end with the real tokenizer. It writes a shard
set, it reads back with every span invariant intact, and it fails the S4 padding gate at
26.14% against a <= 15% threshold. Two defects were found and fixed; a third is recorded as
a decision for a human; the pointer head's candidate rule was measured further and not
touched.

### At `write_shards` — the two classes real data actually produces

**`caps:payload_over_render_cap` — 4 of 325 rows, both runs. Correct refusal, wrong
handling (fixed, §5).** Example:

```
cpft:code.change_scope:337876fdd3c3089b82a03d4fe63926814abdc9b8:2100e9f68dff:
REFUSED [context_bytes]: expected 'at most 131072 bytes', got 144554 -- refused rather
```

These are this repository's own largest files — `ledger.py`, `shards.py` — whose
`code.change_scope` and `code.commit_intent` contexts carry both the before and the after
contents and so run to ~150 KB against a 131,072-byte cap. The *refusal* is right. What was
wrong is that it killed the whole write; see §5.

**`span:line_starts_collapse_under_bpe` — 78 of 78 span rows in run B. Correct, and very
expensive.** Example:

```
row 'squad:qa.answer_span:AUDIT/devmap-audit-2026-09-19.md:ans' slot 'evidence':
16 context lines map to only 14 distinct tokens, so two lines share one candidate and
the pointer head cannot tell them apart.
```

The coordinator measured 60.1% of *source files* refused. Measured here over *prose with
ordinary Markdown paragraph spacing*: **100%** — not one span row survived, and run B's shard
set contains zero pointer-head supervision while every other check on it stays green. Run A
is the same corpus with runs of two or more blank lines collapsed to one; there, 78 of 78
span rows write. **That difference is the entire effect of one vocabulary entry.** This lane
did not change the candidate rule — it is `Context::line_starts`' and a live plan decision
recorded as `GAP-S4-LINE-STARTS-COLLAPSE-UNDER-BPE` with three measured options. Run A is
the workaround, and it is a workaround: real corpora have blank lines.

## 4. Length, buckets, padding — the S4 gate FAILS

Run A, 321 sequences: min 320, max 34,522, mean 7,743.

```
choose_buckets -> [479, 2947, 5383, 7072, 8153, 10869, 14759, 34522]
occupancy       -> {0: 42, 1: 39, 2: 40, 3: 40, 4: 40, 5: 40, 6: 40, 7: 40}
padding_waste   -> Ran(passed=False, value=0.261407)
                   879730 padding of 3365371 positions (26.14%); gate is <= 15%
```

Run B, 243 sequences: `[4987, 6181, 7374, 8153, 10134, 12488, 16305, 34522]`, **19.86%**
(605,852 of 3,050,001).

**Diagnosis.** `choose_buckets` takes eight equal-count quantiles, so the top bucket always
holds the top 12.5% of lengths. On a real code corpus that tail runs 14,759 -> 34,522, and
those 40 sequences pay ~50% waste on their own. The threshold was never exercised before
because the byte-level fixture's corpus is synthetic and short.

**Not touched.** `MAX_PADDING_WASTE` is read-only under rule 2, and `choose_buckets`' own
docstring says lowering waste by bucketing better is the work the gate exists to demand.
Changing the bucketing strategy is a plan decision, not a measurement lane's. The option
space a human should choose from: more buckets; log-spaced rather than equal-count
boundaries; a length cap that refuses the tail at write time; or accepting the number.

**Render caps.** Yes, real rows exceed them: 4 of 325, all `max_context_bytes`. No row
exceeded `max_rendered_bytes`, `max_question_bytes`, `max_task_bytes` or `max_option_bytes`.

## 5. What was fixed

Both fixes are in `qd_train/shards.py`, and both are the same class stated twice: **the
writer must say what it did and what it did not do.** Diff: `python/qd_train/shards.py`
+135/-13, `python/tests/test_shards.py` +149/-0. Five new tests; `test_shards.py` goes from
76 collected to 81 — measured, both numbers. The whole-suite figure moved from 1224 (row
`573204c9-...`, at commit `f6d566c`) to 1238 (row `5bae4b06-...`, at `0632f69`); only 5 of
that +14 are this lane's, the rest belong to the two commits other lanes landed in between.
**Not committed**, per the brief.

### Fix 1 — a row the renderer refuses is counted, not fatal

`ContextTooLargeRefusal` is a `QdRefusal`, not an `UnencodableGold`. The writer's `except`
named only the latter, so `allow_unencodable=True` — documented as *"writes the rest and
records the exclusion ... never silent"* — did not cover it. The whole write died at the
first over-cap row, after 316 rows of tokenization, with no `coverage.json` written and no
count of anything.

Pre-fix failure, from the real corpus:

```
  File "python/qd_train/shards.py", line 891, in write_shards
    for spec in training_texts(row, seed=shuffle_seed, caps=caps):
qd_data.errors.ContextTooLargeRefusal: REFUSED [context_bytes]: expected 'at most 131072
bytes', got 144554
```

Pre-fix failure of the new test, in the repo venv, against unmodified code:

```
FAILED test_a_row_the_renderer_refuses_is_excluded_and_counted_not_fatal
E  qd_data.errors.ContextTooLargeRefusal: REFUSED [context_bytes]: expected 'at most 512
   bytes', got 1144 -- refused rather than truncated: ...
```

The fix widens one `except` to `(UnencodableGold, QdRefusal)`. `ShardContractViolation` and
`TokenNotInRemap` are outside `QdRefusal` by construction and still escape: those say the
artifacts disagree with each other, not that one row is unusable.
`test_a_renderer_refusal_without_the_flag_still_refuses_the_whole_write` pins that the
default is unchanged — no flag, no partial corpus, and the original exception.

### Fix 2 — a shard set now says whether its spans were decode-verified

**This is the finding worth most.** `write_shards`' `decode=` argument is the only check in
the module that does not consult the offsets it is checking
(`GAP-S4-GOLD-ON-CANDIDATE-CANNOT-CATCH-LINE-SHIFT` records why nothing else can), and its
own docstring says *"a run that omits it has not had its span mapping verified."* Measured
with the real tokenizer, writing the same corpus with `decode=` and without produced:

* a byte-identical `header.json` (modulo `created_at`),
* a byte-identical `coverage.json`,
* an identical `ShardReader.to_json()` — which is what a ledger row carries.

So "the one check that can catch a consistently wrong line mapping was never run" and "it ran
and passed" read the same everywhere downstream. That is precisely the thing this repository
refuses to let happen, at the artifact level.

Pre-fix failure of the new test:

```
FAILED test_a_shard_set_records_whether_its_span_mapping_was_decode_verified
E  AssertionError: a shard set must state whether its span mapping was verified against
   decoded text; to_json() carries only ['checks', 'coverage', 'header', 'padding_waste',
   'root']
```

The fix adds `span_check.json` beside `coverage.json`, a tri-state with three answers and
never two: `Ran(passed=True, n, n_total)` when `decode` ran, `NotRun` when it was not
supplied, and `NotRun` again when the set holds no span rows at all — 0 of 0 verified is not
a pass, the same rule `artifacts.padding_waste` follows for an empty input. `ShardReader`
exposes it as `.span_check`, an absent file reads as `NotRun`, and `to_json()` carries it.
Verified end to end in run A: `artifacts that differ: ['span_check']`,
`ShardReader.to_json() identical: False`.

## 6. What the read-back said, and what I looked for and did not find

`ShardReader` opened both shard sets and yielded a full epoch. Run A: 321 sequences, 74
batches, 321 rows across them — one sequence per row, so SAFETY-2 holds on real data. Over
every span row (78) and every sequence (321):

```
gold_off_candidate: 0   candidate_in_padding: 0
target_not_before_last: 0   tail_not_one_letter: 0   decode_mismatch: 0
```

Three things I went looking for and did **not** find, stated because a negative that was
actually tested is worth more than silence:

1. **`target_index = lengths - 2` assumes the trailing answer letter is a token of its own.**
   In byte space that cannot fail. Under Qwen's pretokenizer `>A` is one chunk, so `>` and
   the letter could plausibly merge. Probed over all 17 letters including `noul`, then over
   all 321 written sequences: the letter is always its own final token and
   `target_index` is always `lengths - 2`. **The convention holds.** `<|qd_answer|>` itself
   is not a special token in this vocabulary — it tokenizes as six ordinary pieces
   (`'<','|','qd','_answer','|','>'`), which is fine but worth knowing.
2. **`tokenizer.decode` with no kwargs.** `_assert_spans_decode_to_their_text` requires the
   ids to round-trip, and HuggingFace's `clean_up_tokenization_spaces` rewrites punctuation
   spacing over a sequence. If the default rewrote, passing `tokenizer.decode` straight into
   `write_shards` — the obvious call — would refuse every span row with a message about
   offsets. Measured: the default is accepted. A caller need not know to pass
   `clean_up_tokenization_spaces=False`.
3. **Offsets describing a normalised copy.** The `reach != len(text)` check never fired over
   321 sequences.

One measured fact that is **accepted by design and had never been counted**: of 1,598
accepted line-start candidates in run A, **234 (14.6%) sit inside a token that begins
earlier in the text** — i.e. the position the pointer head is asked to select is a token
that starts mid-previous-line. `_token_index_for_char` documents that it takes the token
*containing* the line start, so this is not a defect; but 14.6% is the size of what that
rule is silently doing, and the serving side must resolve a line start to a token the same
way or the two disagree on one candidate in seven.

## 7. What is open

* **`GAP-PIPELINE-REMAP-DEMANDED-BEFORE-EXCLUSION`** (new, open). `write_shards` calls
  `RemapTable.encode` *before* `_span_token_positions` decides whether the row is
  excludable, so with `allow_unencodable=True` a row the writer is about to drop can still
  abort the whole write. Reproduced: a remap built by `count_corpus_tokens` over the 243
  sequences that actually reach the shard set raised `TokenNotInRemap` — *"8 of 322 token(s)
  were dropped by the remap; the first is old id 32766 at position 66"* — for a span row
  that would have been excluded three lines later. The corpus that would have been written
  is fully covered by that remap. It fails closed rather than silently, and `shards.py`
  carries an explicit comment placing that `encode` where it is, so reordering a check the
  author deliberately positioned is a human's call. **It constrains S2**: the remap must be
  counted over every row in the manifest, not over the rows that survive the writer.
* **`GAP-S4-LINE-STARTS-COLLAPSE-UNDER-BPE`** (existing, untouched). This lane adds a second
  measurement: 100% of span rows refused on real Markdown prose, against the coordinator's
  60.1% on source files.
* **`GAP-PIPELINE-DEVMAP-LOWER-BOUND-AND-GITPULSE-BLIND-TO-THIS-WORKTREE`** (new, open).
  DevMap's index was built and fresh (generation 845, 3,622 nodes, 11,739 edges, 0 pending)
  and named `python/tests/test_shards.py` as the only consumer of `ShardReader`, but every
  walk returned `walk_incomplete` with a repository-wide unresolved-site count, so that is a
  lower bound; it was corroborated with `rg -uu` over `python/`, `docs/` and `tools/`, which
  agreed. GitPulse reported every facet `ok` and `overlapping_files: 0` while another lane
  was concurrently committing to this worktree and holding `python/qd_train/ledger.py`,
  `python/qd_train/mutate_adapter.py` and their tests dirty — the zero answers a
  between-worktrees question, already recorded as
  `GAP-GATES-GITPULSE-BLIND-TO-SAME-WORKTREE-LANES`. Standing tool limitations:
  `GAP-DEVMAP-WALKINCOMPLETE`.

**Not run, and why.** No GPU suite, no training step, no model: this lane tokenizes a corpus
and writes shards. `noul_rate` is `NotRun` in both rows for that reason. The `bigcode/commitpackft`
and `nuprl/AgentPack` pools were not read — the HF datasets-server was returning HTTP 500
throughout, and `nuprl/AgentPack` is gated. So **every number here is from one repository's
own history and is a subsample**, which is why both rows are `quick`.
