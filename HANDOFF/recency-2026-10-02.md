## The finding: F's three seeds trained on one batch order [V]

`real_ft_run.main` at F's commit `a502670` does three things, read directly from an export of that
commit:

- It builds the epoch plan once, at `DataConfig().seed`. The plan is
  `plan_all = list(reader.batches(batch_tokens=batch_tokens, seed=config.seed, epoch=0))`
  (`tools/real_ft_run.py:8466`), with `config = DataConfig()` at `:8140`. `qd_data/config.py:53`
  defaults that seed to 20260919, and nothing in `main` sets it from `--seeds`.
- It hands that same list to `_train` for every seed in `--seeds` (`:8707`).
- It never reorders the list. `_train`'s `source()` yields it in order (`:2365-2375`), and
  `train_ft` consumes the iterator as given.

The ft rows agree with this reading: for each seed, `micro_batches == optimizer_steps == batches
== 9683`, `passes = 1` and `termination = steps_exhausted`. That rules out a resume, a cap and
gradient accumulation. So step *i* of every seed trained plan batch *i* of one plan.

The training seed sets other things: the span head's random init and the training RNG stream
(`backbone.py`, `torch.manual_seed(seed)`). With default kernels (`deterministic: false`), kernel
nondeterminism adds the rest.

**Consequence.** (a) and (b) below are one number each, identical for seeds 0, 1 and 2. The
ruling's test was that a seed holding prose abstention should have more prose-noul rows late.
That test cannot be run on F, because the late rows are the same rows on every seed. So recency
cannot be what separates 54/60 from 0/60 and 1/60. This is a fact about the code and the plan, not
a causal claim about abstention; n = 3.

The code still does this at `a3c09de` (main): `real_ft_run.py:10301`, `:10674`, `:10976`. Three
places say the opposite:

- `python/qd_train/backbone.py:1064` says the seed "determined the BATCH ORDER".
- `python/qd_train/trainer.py:692` says "the batch order is a function of the seed".
- `campaign/f-v4-preregistered.json` says J6(f) uses "same data order as F seed 0".

That last one holds for every F seed. Recorded as
`GAP-REAL-FT-RUN-BATCH-ORDER-IGNORES-THE-TRAINING-SEED-2026-10-02`. Report-only; nothing changed.

## Premise corrections

1. **"Three batch plans, deterministic per seed."** There is one plan, above.
2. **`--option-permutation-seed 20260919` is J6(g)'s flag, not F's.** The J6(g) prelude's argv
   carries it (`/Users/bharath/qd-campaign/j6g-prelude-2026-10-02/run_prelude.sh:71`). F's recipe
   has no `option_permutation_seed` key [V]. The flag permutes letters inside a batch and would not
   move membership anyway.
3. **The J6(g) capture technique was not reused**, for three reasons:
   - It runs `real_ft_run.main` with `--devices mps`, and its log shows MPS bucket probes before
     `Ledger(...)` (`prelude.log`). That is MPS work, which this lane may not do.
   - It took 20.2 GB.
   - `main` reaches the plan through `reader.batches`, whose order is `ShardReader._plan`. This
     tool calls that function directly on the same shard set, with the same `(seed, epoch,
     batch_tokens)`, through `a502670`'s own `ShardReader`.

   This run took 38 s at 1.57 GB max RSS.
4. **Code commit.** F's own commit `a502670` was used: `code_commit` on all six F rows, the same
   commit the J6(g) prelude used. It came from a fresh `git archive` export, not from L-j6g's
   worktree.
