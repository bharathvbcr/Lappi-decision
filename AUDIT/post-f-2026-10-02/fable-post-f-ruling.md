Before anyone writes a kernel: (1) time `qd_runtime::sha256` alone over a host-resident copy of the same 221 MB; (2) separately time `try_contents_u8()` after an explicit synchronize. If (1) is ~2 GB/s, the cost is the map/sync, and the fix is to take the digest off the critical path (after the answer is returned, on the copy) or to digest only on write-back; if (1) is ~0.45 GB/s, the software SHA path is in use and the crate's hardware backend is the one-line fix worth ~4-5×. Only if a host digest cannot get under ~10% of latency does a device digest earn its place, and then it goes into canonical tessl by its owner (`AUDIT/metal-digest-2026-10-02/state_digest.metal` is the proposal). Rule 6 keeps Lappi kernel-free: do not ask the human for a qd-metal overlay `build.rs`; it stands up a second kernel-building path beside tessl. A non-cryptographic digest (xxh3-class) would suffice for a runtime read-only guard but is a new dependency and a semantic change to a recorded identity, so it needs the human's yes if proposed.
