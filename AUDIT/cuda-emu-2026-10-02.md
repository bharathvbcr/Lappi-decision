# cuda_emu: evidence for the claims its design rests on (2026-10-02)

Lane L-cuda-emu. Environment: a Linux x86_64 cloud container (4 vCPU) with Ubuntu clang 18.1.3,
libstdc++ 13, libc++ 18 (`libc++-18-dev`, installed for this check), g++ 13.3.0 and rustc 1.97.0.
It is **not** the Mac the ojas crate lives on. Every claim below was measured here, and none of
it is a GPU result.

## 1. Under TSan, libc++'s `std::barrier` reports races in a correctly barriered program

The brief said `__syncthreads` would be a block `std::barrier`. With libc++, ThreadSanitizer cannot
see that barrier's synchronisation, so every barrier-ordered access is reported as a race.

Program (four threads: each writes its own slot, `arrive_and_wait`, then reads every slot):

```cpp
#include <barrier>
#include <cstdio>
#include <thread>
#include <vector>
int main() {
  std::barrier<> bar(4);
  int slot[4] = {0, 0, 0, 0};
  std::vector<std::thread> ts;
  for (int i = 0; i < 4; ++i)
    ts.emplace_back([&, i] {
      slot[i] = i + 1;
      bar.arrive_and_wait();
      int sum = 0;
      for (int j = 0; j < 4; ++j) sum += slot[j];
      if (sum != 10) std::printf("bad sum %d\n", sum);
    });
  for (auto& t : ts) t.join();
  std::puts("done");
}
```

`clang++ -std=c++20 -O1 -g -fsanitize=thread -stdlib=$LIB barrier_tsan.cpp`, run three times each
with `TSAN_OPTIONS=exitcode=66`:

| `-stdlib=` | runs | exit | `WARNING: ThreadSanitizer: data race` |
| --- | --- | --- | --- |
| libstdc++ | 3 | 0, 0, 0 | 0, 0, 0 |
| libc++ | 3 | 66, 66, 66 | 1, 1, 1 |

The reported pair was the pre-barrier write `slot[i] = i + 1` and a post-barrier read of `slot[j]`.
Apple's libc++ build was not checked. The emulator no longer uses `std::barrier`, so the
result does not change either way.

**Consequence:** `cuda_emu.h` rendezvouses through a mutex and one condition variable per thread.
TSan sees mutexes and condition variables on every platform, and the exact deadlock detector
needs the per-thread state that this structure gives it.

## 2. A rendezvous mutex that TSan can see hides a missing `__syncthreads`

The first version gave each block one mutex for every barrier and warp collective. Under TSan, the
self-test `missing_syncthreads_is_reported_as_a_race_under_tsan` failed with
`expected Race, but the run succeeded`. TSan counts every unlock/lock pair as a happens-before
edge, so two warps that each did a shuffle were "ordered" even though no barrier separated their
write and read of `partial[]`.

**Consequence:** in the Thread mode the emulator's bookkeeping runs inside
`AnnotateIgnore{Reads,Writes,Sync}{Begin,End}`. The only edges reported to TSan are the ones CUDA
guarantees: `__tsan_release`/`__tsan_acquire` on per-phase tokens for `__syncthreads*`, and
per-lane tokens for `__syncwarp`. Shuffles, votes, warp reductions and atomics get none.
Three mutations were run against the self-tests, and each was caught:

| mutation of `cuda_emu.h` | test that fails |
| --- | --- |
| keep the mutex visible to TSan (drop `AnnotateIgnoreSync*`) | `missing_syncthreads_is_reported_as_a_race_under_tsan` (race not reported) |
| drop the barrier's `__tsan_release` | `correctly_barriered_kernel_is_race_free_under_tsan` (false race) |
| drop the `__syncwarp` edges | `syncwarp_orders_shared_memory_between_lanes_under_tsan` (false race) |

Both runtimes export the annotation entry points. Clang 18's static TSan runtime has
`AnnotateHappensBefore`, `AnnotateIgnoreReadsBegin`, `AnnotateIgnoreSyncBegin` and
`AnnotateIgnoreWritesBegin`, and GCC's `libtsan.so.2` has the same, per `nm`. Whether Apple's
runtime exports them is not known yet (GAP-CUDAEMU-1002-MAC-TOOLCHAIN-PATHS-UNVERIFIED).

## 3. The TSan runtime also reads `UBSAN_OPTIONS`

With `TSAN_OPTIONS=...:exitcode=66` and `UBSAN_OPTIONS=...:exitcode=67` both set, a TSan race
report exited with status 67. The harness now sets only the active mode's variables and removes
inherited ones.
