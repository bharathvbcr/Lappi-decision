## 3. gemma-metal host quantiser (ojas/gemma-metal, own workspace, `Cargo.toml:37`)
Card cites are stale in line number; the defects are real except as noted:
- bf16 rounding: [V] `quant.rs:572-576` `((bits>>16) as u16).wrapping_add((bits>>15)&1)`. Not RNE: ties round up (no sticky/even test), and NaN with payload only in the low 16 bits (e.g. 0x7F80_0001) truncates to 0x7F80 = +Inf; 0x7FFF_xxxx with bit15 set wraps to 0x8000 (-0). Confirmed. Canonical RNE owners already exist: `ojas_core::f32_to_bf16` (`ojas-core/src/autocast.rs:72`, re-exported by `ojas-io/src/half.rs:20`) and `ojas-cuda/src/bf16.rs:13` (not verified bit-equal to core [U]). Used by `kernels.rs:380-381` (scale/bias upload) and `kernels.rs:5030`, `forward.rs:146`.
- Silent NaN/Inf groups: [V] `affine_params` `quant.rs:452-461` returns `(1.0, 0.0)` when min/max non-finite (used by Q8 and Q4 signed); `quant_q4_mlx` `:372-376` sets lo=hi=0 on the same condition. `f32::min/max` ignore NaN, so a group with some NaN and finite others quantises NaN via `as u8` (saturating cast gives 0): silent. Confirmed, no error returned.
- group size 0: [V] `kernels.rs:377` is no longer a division (now `pack_mlx_sb_bf16` :378). Divisions by group_size are at `kernels.rs:301,341` inside `repack_q4_mlx_*`, reached only via `prefer_blocked/interleaved_q4_mlx` (:268-288) which guard `group_size > 0`; the call sites 2519,2531 [V] sit behind them; sites 5283,5355 call `repack_q4_mlx_blocked` with `group` [U whether guarded]. A separate unguarded `self.rows % self.group_size` at `kernels.rs:2822` would panic on 0 [V line; reachability U]. All quantisers themselves check `group_size == 0` and return Err (quant.rs:166,300,352,415,516). Net: card's "panics" is [U], not shown reachable (matches the 10-15 note).
- Format compatibility with MLX affine:
  - Q4Mlx decode side: [V] unsigned nibble, low nibble = even index, u32 little-endian bytes (`quant.rs:158-222`, comment "u32 LE bytes == our nibble packing"); matches MLX (`quantized.h` affine_quantize: `output |= val << (bits*(i%pack_factor))`). Loading MLX-quantised tensors is compatible.
  - Q4Mlx quantiser: [V] `quant.rs:346-406` is NOT MLX's algorithm: scale=(hi-lo)/15 (eps 1e-8 on range), bias=lo, always positive scale, no edge/"at_zero" snapping, round half away from zero over f32 params; MLX (below) picks the edge by larger |.|, flips scale sign, snaps q0 to integer. Not bit-compatible; ints differ.
  - Q8: [V] `quant.rs:408-448` signed int8, symmetric default (`quantize_affine_f32` passes `symmetric=true`, :246), scale f32, zero f32: `scale*(q-zero)`. MLX q8 is unsigned uint8, `scale*q+bias`, bf16 scale/bias. NOT compatible (layout, signedness, dtype).
  - Hot-bank scale/bias are bf16-rounded only at upload (`kernels.rs:378-382`) after quantisation with f32 params, same as MLX (MLX computes q with f32 scale/bias then stores T-cast scale/bias).
- [I] Conclusion: gemma-metal's quantiser is not reusable as the oracle-exact owner. Write the MLX-exact host quantiser once (ojas-core or new crate), and let gemma-metal later delegate.

## 4. MLX affine format (local: /Users/bharath/.venvs/ml/lib/python3.14/site-packages/mlx, mlx 0.31.2; also ml-2026-10 and ml-next have 0.32.3; Lappi-decision/.venv has no mlx hit [V ls])
Source: `.../mlx/include/mlx/backend/metal/kernels/quantized.h` (Metal GPU kernels; the CPU quantise path in ops/cpu .cpp is not shipped [U equivalence]).
- Packing [V] `affine_quantize` :2432-2530, `get_pack_factor/bytes_per_pack` :18-26: pack_factor = 8/bits per byte; for q8 one uint8 per element; q4 two nibbles per byte, element i in the low bits first (`val << bits*(i%pack_factor)`), so as uint32 (the python array dtype) 8 nibbles (q4) or 4 bytes (q8), little-endian. Shapes: w_q `[rows, cols*bits/32]` uint32; scales, biases `[rows, cols/group_size]` in the INPUT dtype (bf16 for bf16 input) [V doc: "scale type: same as input"; `device T* scales`].
- Scale/bias algorithm [V :2475-2482]: scale = max((max-min)/n_bins, 1e-7) (n_bins = 2^bits-1, computed in f32); `side = |min|>|max|`; scale = side ? scale : -scale; edge = side ? min : max; q0 = round(edge/scale); if q0==0 keep scale and bias=0 else scale = edge/q0, bias = edge. Quantise `q = min(round((w-bias)/scale), n_bins)` (:2496), then scale/bias are cast to T when written. Note the kernel initialises `w_max = 0` (:2459) and `w_min = Limits<T>::max`: [I] groups whose values are all negative see max=0. Also q uses f32 scale before bf16 rounding of the stored scale. A bit-exact host oracle must replicate these, including negative scales and `round` = half away from zero [I, Metal round()].
- Dequant [V :485-,2540+]: `out = scale*q + bias` in T. [U] whether T=bfloat arithmetic fuses/rounds the same as a host f32 path: bit-exactness against `mx.dequantize` must be tested empirically (a Lappi-side numpy/mx fixture), not assumed.
- Supported: affine group {32,64,128}, bits {2,3,4,5,6,8} (docstring from `mx.quantize`, run read-only). Default group 64, bits 4.

## 6. Memory arithmetic [I]
Wrapped-linear element count: MLP 24*3*6144*2048 = 905,969,664; GDN 18*(6144+2048+2048)*2048 = 377,487,360; attention 6*(4096+512+512+2048)*2048 = 88,080,384; total N = 1,371,537,408 (+1.18M for in_proj_a/b).
- bf16: 2N = 2.743 GB. q8 g64 (1 B + 2+2 B scale/bias per 64 = 1.0625 B/elem) = 1.457 GB, saves 1.286 GB. q4 g64 (0.5625 B/elem) = 0.771 GB, saves 1.972 GB.
- Tied embedding/lm_head 248320*2048 = 508.6M * 2 B = 1.017 GB stays bf16 (quantising the tied table also changes the output head; not planned). Resident base: bf16 ~3.77 GB (D3 said ~3.8) vs q8 ~2.47 GB vs q4 ~1.79 GB.
- Step peak: measured full-gradient bf16 step 18.02 GB at T=9,638 after the tied-table win (`tasks/gp-bf16-compute-tier.md:161`); LoRA estimate 13-14 GB [I, `gp-ft-bf16-frozen-base.md:121`]. So the base is ~3.8 of ~13.5 GB (28%) and the quantisable part is 2.74 of 13.5 (20%); q8 removes 1.29 GB (~9.5% of the step), q4 1.97 GB (~15%). Activations and logits are the dominant term: if the logits are materialised, T*V = 9,638*248,320 = 2.39e9 elements = 9.6 GB f32 [U whether chunked/materialised].
- Against the 32 GiB memguard (34.36 GB) [V memory note]: a 13-14 GB LoRA step has ~20 GB headroom in bf16. q8 buys nothing needed to fit; the memguard problem was the f32-tower Qwen35Step (30 GB resident), a different path. Conclusion [I]: on this machine q8 is a quality/serving-parity experiment, not a memory necessity, which is exactly D3's "memory-need" gate: it is not met. The owner's 2026-10-17 decision overrides the gate for building; the arithmetic still says expect ~1.3 GB saving, not a new feasible shape.
